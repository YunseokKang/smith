# 아키텍처 초안

Python 3.11+를 골격의 구현 언어로 선택했다. 아래 DB·검색·어댑터 구성은 설계 제안이며
외부 연동 구현이나 검증을 완료했다는 뜻이 아니다.

## 계층

1. 입력: 토스 조회 어댑터 / JSON importer / 이후 Hermes 조회 어댑터.
2. 정규화·저장: 원천 식별, 중복 제거, 거래/시점별 평가/버전 이력.
3. 계산: 순자산, 현금흐름, 집중도, 조달 비용, 목표 시나리오.
4. 근거: 금리·시황 공급자와 문서 검색. 발표 시점·관측 시점·출처를 보존.
5. 자문: 비식별 allowlist payload + 계산 결과 + 검색 근거 → Claude Code headless.
6. 출력: CLI 응답, 보고서 미리보기, 명시적 발행, 스케줄러, Gmail delivery.

CLI와 향후 앱은 동일한 application service를 호출한다. 웹 서버를 지금 만들 필요는 없다.
`src/smith/ports.py`는 초기 의존성 경계를 표현하는 Protocol이다.

## 저장소 및 RAG

PoC 원장은 표준 라이브러리 `sqlite3`로 구현했다(`src/smith/ledger.py`, 기본 `data/smith.db`).
선택 이유: 의존성 없음, 단일 사용자 규모, 파일 하나로 백업 가능, transaction 지원.
배포 환경과 동시 실행 요구가 확정되면 재검토한다.
원장은 record revision을 추가만 하는 구조다. 공통 열(ID, kind, owner, source, status, 시각,
revision)은 컬럼으로, 종류별 필드는 정규화된 JSON 텍스트로 저장해 계약 확장 시 migration을 줄인다.
가져오기는 `BEGIN IMMEDIATE` transaction으로 직렬화하며, 스키마 버전은 `PRAGMA user_version`으로 관리한다.
스키마 생성·migration은 쓰기 경로(`import`, `toss sync`)에서만 한다. 미리보기와 조회는 원장을
읽기 전용(`mode=ro`)으로 열고, 구버전 스키마면 메모리 사본을 migration해서 읽는다. 파일은 바꾸지 않는다.
스키마 v2는 순자산에 넣지 않는 참고 지표(매수 가능 금액, 환율)를 담는 `observations` 표를,
v3는 공급자 동기화 시도의 성공·실패를 남기는 `sync_runs` 표를 추가했다.

## 계산 (2단계, `src/smith/summary.py`)

`smith summary`는 원장만 읽어 결정적으로 계산한다. LLM은 이 수치를 계산하지 않는다.
- 기준 통화 KRW. 환산은 `as_of`·`known_at` 이전의 최신 `fx_mid_rate` 관측값을 쓴다.
  환율이 없는 통화의 자산·부채는 합계에 넣지 않고 "미환산"으로 분리해 요약을 불완전으로 표시한다.
- 가계 전체를 합산하되 소유자별 순자산도 따로 보인다(법적 명의에 따라 세금·대출 판단이 달라짐).
- 순자산 = 활성 자산 평가액 − 활성 부채 잔여 원금. 보험 보장액, 매수 가능 금액, 마이너스통장 한도는 제외.
- 자산 배분: 자산 유형·계좌 유형·통화·유동성별 금액과 비중.
- 월 현금흐름: `as_of` 날짜에 유효한 반복 흐름을 월 단위로 환산(분기 ÷3, 연 ÷12, 곱셈 대신 나눗셈).
  `internal_transfer`는 수입·지출과 분리하고, 1회성 흐름은 향후 12개월 예정 항목으로 따로 보인다.
- 대출 이자 추정: 연결된 부채의 잔여 원금 × 연이율 ÷ 12. 추정치로 표시한다.
- 데이터 신선도: 원천별 기준 시각 범위. 수동 90일, API 7일, 환율·매수 가능 금액 7일을 넘으면 경고한다.
  마지막 동기화 실패가 마지막 성공보다 늦으면 경고하고, 원천별 마지막 성공·실패 시각을 표시한다.
- 완전성: 환산하지 못해 합계에서 빠진 항목이 있으면 영역(`balance_sheet`, `cash_flow`, `goals`)을
  `incomplete_areas`에 남기고 `complete=false`로 표시한다. 0 이하 환율은 없는 환율로 취급한다.
- 알 수 없는 자산 분류는 중단하지 않고 `other`로 집계하며 경고한다(분류 변경 정책).
- `--json`은 금액을 문자열로 내보낸다. 5단계 LLM payload의 입력이 된다(비식별화는 5단계에서 추가).
잔고·현금흐름·거래는 구조화된 DB에 저장한다. RAG는 약관·상품 문서·외부 자료·과거 자문을
검색하는 데 사용하며 수치의 원장으로 사용하지 않는다. 문서가 적으면 전문 검색부터 시작해
필요할 때 임베딩 검색을 추가한다. 출처, 문서 버전, 유효 기간과 인용 위치를 보존한다.

## 근거 (4단계, `src/smith/evidence.py`)

1차 범위는 한국·미국 금리다. 2026-10-04 실제 API로 코드와 응답 형식을 확인했다.
- ECOS `StatisticSearch`(일별 `D`): 기준금리 `722Y001/0101000`, 국고채 3년 `817Y002/010200000`,
  10년 `817Y002/010210000`, CD 91일 `817Y002/010502000`, 원/달러 매매기준율 `731Y001/0000001`.
  오류와 빈 결과는 HTTP 200 안의 `RESULT.CODE`로 온다(`INFO-200`은 데이터 없음).
- FRED `series/observations`: `DFEDTARU`, `DFF`, `DGS2`, `DGS10`, `MORTGAGE30US`. 결측은 `"."`이며 0이 아니다.
  `realtime_start`는 FRED 실시간 기간의 시작일이지 발표일이 아니므로 발표일(`published_on`)은 비워 둔다.
- 설정한 시계열은 모두 필수다. 하나라도 관측값이 없으면 그 공급자 전체를 `missing-series:<id>` 실패로
  기록하고 저장하지 않는다(이전 값이 새로 확인된 것처럼 보이지 않도록).
- `retrieved_at`은 응답을 모두 받은 뒤의 시각이다(동기화 시도 시각과 분리). 기존 값 읽기·비교·삽입은
  `BEGIN IMMEDIATE` 하나 안에서 해 동시 실행에서도 같은 값이 두 번 들어가지 않는다.
- 원장 v4 `evidence_points`: 관측일·값·발표일·조회 시각. 값이 바뀐 경우에만 새 행을 추가하므로
  공급자가 과거 값을 수정해도 이전 보고서의 근거를 `known_at`으로 재현할 수 있다.
- 공급자 하나가 실패해도 다른 공급자는 저장한다(누락이 자산 오판으로 이어지지 않으므로). 결과는 `sync_runs`.
- 키는 OS 자격 증명 저장소(`smith.ecos`, `smith.fred`)에 두며 URL에 실리므로 URL·원본 오류를 출력하지 않는다.
- `smith evidence show`: 최신 값, 약 3개월·12개월 전 대비 변화(기준점이 2주 넘게 떨어지면 미표시),
  관측일, 출처, 오래됨(일별 10일, 주간 14일) 표시.
- 공식 발표문(`src/smith/announcements.py`, 원장 v5 `announcements`): Fed 통화정책 보도자료,
  한국은행 총재 기자간담회(`B0000169`)·금통위 의사록(`B0000245`) RSS의 제목·링크·발표 시각만 저장한다.
  피드는 신뢰하지 않는 외부 데이터다. 2MB 제한, 발행 기관 도메인의 https 링크만 허용(파싱할 수 없는 링크는
  해당 항목만 버림), 제목은 제어·폭 없는·방향 제어 문자와 유니코드 줄 구분자를 제거한 뒤 300자로 자르고,
  어떤 내용도 지시로 해석하지 않는다. 제목이나 발표 시각이 바뀌면 새 버전으로 쌓아 `known_at` 재현을 지원한다.
  본문은 5단계에서 필요할 때 가져온다.
  한국은행 통화정책방향 결정문 게시판의 RSS 주소는 확인하지 못해 추측하지 않았다.
- 개인 자산 관련성(`src/smith/relevance.py`): 원장에서 변동금리 부채, 원화 현금·예금, 달러 자산,
  주식·구성 미상 증권, 부동산, 만기 있는 임대보증금 반환 의무의 금액·비중을 결정적으로 계산하고
  관련 시계열·피드를 연결한다. 인과 해석은 5단계 자문이 맡는다. 원장이 불완전하면(미환산 등) 결과에
  `complete=false`와 미환산 금액을 담고 자산 대비 비중은 표시하지 않는다(분모가 불완전하므로).
- 일관된 읽기: 요약·노출·`evidence show`는 `ledger.snapshot()` 읽기 트랜잭션 하나에서 읽어,
  중간에 들어온 import가 분자와 분모를 서로 다른 시점으로 만들지 않게 한다.
- 모든 외부 HTTP 요청(토스, ECOS, FRED, RSS)은 리디렉션을 따르지 않는다(`src/smith/net.py`).
  따라가면 토스 token이나 URL의 API 키가 다른 호스트로 전달되거나 외부 문서가 공식 출처로 저장될 수 있다.
  3xx는 실패로 기록하고, 출처 주소가 바뀌면 확인 후 코드의 주소를 갱신한다.

## 자문 (5단계)

`smith advise --case portfolio|funding|home [--question] [--show-payload]`.
- 원장 뷰(`src/smith/payload.py`): 한 스냅샷에서 요약·레코드·노출·근거·발표를 읽는다. 레코드 ID는
  A*/L*/C*/G* 별칭으로, 노출은 X*로 바꾼다. 소유자 ID는 `self` 또는 `household_member_*`, 원천 ID는
  경고 안에서 S*로 바꾼다. 사용자 지정 질문에 같은 내부 ID가 있으면 전송 전에 동일하게 치환한다.
  별칭과 실제 레코드 ID의 대응은 로컬 출력에만 쓴다.
  허용한 필드만 보내며 `reason`, 계좌 키, 기관명이 들어간 ID는 보내지 않는다. 종목 심볼은 포트폴리오
  사례에서만 보낸다. 금액은 원 단위 정수 문자열이다.
- 차단(AC-07): 질문과 payload 전체에서 계좌번호·카드번호·주민번호·이메일·전화번호, 명시적으로 표기한
  이름·한/영문 주소 패턴과 저장된 토스·ECOS·FRED 키 문자열을 찾으면 보내지 않고 규칙 이름만 출력한다.
  자격 증명 저장소를 읽을 수 없어도 fail closed한다. 입력은 UTF-8 500,000 bytes로 제한한다.
- 사례별 결정적 계산(`src/smith/cases.py`): 포트폴리오(집중도, 달러 비중, 유동성 개월, 부채 비율, 보험료·
  재량 지출), 긴급 조달(본인 자산의 조달 단계별 금액·누계·부족분, 미실현 손익, 해외주식 양도세 추정 —
  손익 통산, 22%·250만 원 공제는 가정), 주택 이동(기준·유리·불리 시나리오의 필요 자금, 본인 가용액,
  부족분, 배우자 부동산 순자산 포함 시 부족분). 누락 환율·원가는 0으로 바꾸지 않고 관련 합계와 판단을
  `null`로 전파한다. 현금흐름은 기준일에 활성인 반복 항목만 쓰고 주택의 본인 가용액에는 본인 흐름만
  반영하며, 원금 상환 추정은 해당 주택 담보대출의 지급액과 이자만 쓴다. 가정값은 모두 결과에 남긴다.
- headless 경계(`src/smith/adviser.py`, Claude Code 2.1.195에서 확인): 네이티브 `claude.exe`를 직접 실행
  (`.cmd` 래퍼는 cmd.exe 인자 해석 때문에 실행 거부), 질문·payload는 stdin, `--tools ""`, `--safe-mode`,
  `--no-session-persistence`, `--system-prompt-file`(작업 폴더의 파일. 인자로 넘기면 Windows 명령줄 32,767자 한도에 걸린다, BUG-2026-005), `--output-format json`, `--json-schema`,
  `--max-budget-usd`(기본 5.00, 폭주 방지용 상한), 기본 모델 `fable`(가장 강한 추론 모델, 사용자 결정 2026-10-05). "추가 과금 없음"은 운영 환경 가정이다: 현재 Claude Code가 정액 구독 로그인으로 인증되어 있다는 사실에 기대며, 코드가 보장하지 않는다. 허용 환경변수에 `ANTHROPIC_API_KEY`가 있으므로 그 키가 설정되면 API 과금이 된다. OAuth 인증에서 예산 상한의 의미는 문서화되어 있지 않다. 빈 임시 작업 디렉터리, 환경변수 허용 목록,
  `SMITH_HEADLESS=1`(이 값이 있으면 `smith advise`가 거부해 재귀 실행을 막는다), 300초 제한, 출력 1MB 제한.
- 출력 검증: CLI에는 최소 스키마를 넘긴다(길이·최대 개수·추가 필드 제약이 있으면 실제
  payload에서 `error_max_structured_output_retries`가 났다). 받은 뒤 알 수 없는 필드는 버리고 길이·개수·
  타입을 엄격히 검증하며, refs 필드뿐 아니라 본문에 존재하지 않는 참조를 쓰면 거부한다. 실패 시 세부
  정보는 필드 경로·참조 이름·CLI 결과 subtype만 출력한다.
  5단계는 자유 서술에 나온 모든 숫자가 계산 결과에서 왔는지까지 기계적으로 대조하지는 않는다. 프롬프트로
  제한하고 있으며, 숫자 출처 검증기는 6단계 보고서 설계(`docs/report-design.md` §5)에 제안으로 남아 있다.
- Hermes 운용 자산(`managed_by=hermes`)은 직접 매각·변경을 권하지 않도록 지시하고, 조달 단계에서도
  뒤쪽에 둔다.
- 기록(원장 v6 `advice_runs`): 질문, stdin으로 보낸 것과 동일한 payload 원문과 해시, 프롬프트 버전,
  모델, 비용, 결과 또는 오류. 성공 결과를 기록할 수 없으면 화면에도 자문을 내보내지 않는다.
- 2026-10-04 검토 전 구현으로 실제 데이터의 세 사례가 모두 성공했다(사례당 약 $0.4~0.55).
  검토 수정과 advice-v4 문체 변경 뒤에는 비용이 드는 실제 호출을 다시 하지 않았고 단위 테스트로 경계를 검증했다.

## 조사·서술·검증 (§10 2차, `research.py`, `narrative.py`, `headless.py`)

모든 모델 호출은 `src/smith/headless.py`의 같은 경계(표준 입력, `--safe-mode`, 세션 비저장, 시스템 프롬프트 교체,
구조화 출력 재검증, 빈 임시 디렉터리, 환경변수 허용 목록, 시간·비용 상한, 재귀 실행 차단, MCP 도구 명시 거부

- **검증**(6d, 코드, 블록마다):
  - 참조는 입력에 있는 것만, 본문에 참조 코드 금지.
  - 외부 사실 표현(정책·규제·금리·시장 등 표지어)이 있으면 R/N 출처 필수. 시사점·제안 맥락은 항상 필수.
  - 법·세제·대출 규칙 표현이 있으면 `official` 등급 R 또는 N 출처, 그리고 "확인" 문구 필수.
  - 확정 표현(반드시 오른다, 보장된다, 승인이 확실하다)과 주택 수 단정(다주택자입니다 등) 거부.
  - 숫자는 부호를 포함해 비교한다. 단위(%·억·만·원 등)가 붙은 숫자는 근거 입력의 수치 또는 그 블록이 인용한 R 항목의
    수치에 있어야 한다. 단위 없는 작은 개수·월·연도만 예외.
  - **근거 입력은 허용 목록이다**(`narrative._EVIDENCE_KEYS`): 코드가 계산한 결정적 입력(원장 맥락, 변화, 제안, 전략,
    가정, 소유 메모, 실거래, 분야 지표, 가구 정보, 세금, 날짜)과 고객의 말(이번 질문, 같은 스레드의 고객 발언, 고객
    기억)만 들어간다. 조사 브리프는 블록이 인용한 항목만, URL은 제외. 모델 출력(보고서 서술 `recent_report`, 수정 전
    출력, 전문가 발견 사항, Smith의 이전 답)은 어떤 키로 들어와도 근거가 아니다. 새 입력 키는 목록에 넣기 전까지 근거가
    되지 않는다(2026-10-07 리뷰: 제외 목록 방식에서 `recent_report` 숫자가 근거로 인정되던 구멍을 막음).
  - 금액 표기("1억 350만 원", "3.4억 원", "85,000원")는 원 단위 금액으로 환산해, 쓰인 정밀도 범위 안에서 입력 금액과
    대조한다(금액 비교는 부호를 보지 않는다). 근거 쪽(입력과 고객의 말)에서는 "원" 없는 "21억"도 금액으로 읽는다.
    블록이 쓴 문장은 "원"이 있어야 금액으로 읽는다.
  - **퍼센트는 퍼센트 후보하고만 대조한다**(`_percents`): 비율 필드(`share`, `return_on_cost`, `loan_to_value`,
    `annual_rate` 등)와 제안 수치 중 1 미만 소수는 100을 곱하고, 단위가 "%"인 근거 시계열 값은 그대로, 모든 글 속
    "N%"는 쓴 그대로 넣는다. 블록의 "N%"는 이 후보와 같은 부호이고, 쓴 자릿수의 절반 단위 안이면 통과한다
    ("-67.6%"는 -0.6755와 맞음, "-0.7%"·"-0.6755%"는 아님, 이미 퍼센트인 3.5를 "350%"로 쓰면 아님, 1.0000은 "100%")
    (2026-10-07: 정확히 반올림한 수익률의 탈락을 고친 뒤, 리뷰에서 모든 숫자를 한 집합에 넣어 100배 틀린 값도 통과하던
    결함을 찾아 이 방식으로 바꿈).

    밝히는 쪽을 택함, 2026-10-05). 메모는 사유별 문구(출처 미확인, 확정 표현, 법령 확인 필요, 원장에 없는 수치 등)이며

  모델을 부르지 않고 도구도 없다(같은 headless 경계). ① 전문가 5명(유동성·현금흐름, 부채·금리, 투자·포트폴리오,

  버전 `team-v2`(v1은 인용 가능한 참조를 알려 주지 않아 발견 사항 대부분이 `unknown-ref`로 걸렸다). 시간: 전문가 5분 + 편집자 작성·수정 각 15분. 편집자는 단일보다 입력이 커서(약 70KB 대 50KB) 실제

## 출처 페이지 확인 (`src/smith/sources.py`)

조사 항목의 URL은 호스트만으로 공식 여부를 정했었다. 이제 브리프를 저장하기 전에 각 출처 페이지를 실제로 연다.
- SSRF·DNS 재바인딩 방어: 호스트를 한 번 해석해 모든 주소가 공인 주소인지 확인하고, 그 주소로 직접 연결한다(TLS
  인증서는 호스트 이름으로 검증). 리디렉션은 직접 따라가며 최대 3회, 매 단계 같은 검사를 한다. https·기본 포트만.
- 주장-본문 대응: 항목 제목·설명의 숫자(연도·한 자리 수 제외)를 페이지 본문에서 찾는다.
- 저장: 항목마다 `check`(상태, 최종 URL, HTTP 상태, 확인 시각, 본문 SHA-256, 맞은 숫자 수).
- 결과(관대하게, 걱정은 표시): 없어진 페이지(404·410)·없는 도메인·사설 주소는 뺀다. 숫자 절반 이상 일치는
  `matched`, 확인할 숫자가 없거나 PDF 등은 `reachable`, 숫자가 하나도 없으면 `mismatch`(참고로만 남기고 공식 출처로
  쓰지 않음), 차단·시간 초과는 `unchecked`(호스트 등급 유지). 리디렉션된 공식 링크의 등급은 최종 호스트로 정한다.
- 보고서 푸터에 "출처 페이지를 직접 열어 N건 확인, M건 본문에서 같은 수치"를 적는다. 실제 브리프 22건 기준 3초,
  21건 일치(2026-10-05).

## 세금 관점 (FR-17, `src/smith/tax.py`)

결정적 계산과 규칙 메모. 세법 상수는 기준 연도(현재 2026년, 개정안 반영 전)를 달고, 보고서는 "현행 법령 확인 필요"를 붙인다.
- 연금계좌: `internal_transfer`의 `target_record_id`가 가리키는 계좌 유형별로 올해 납입액(남은 달 포함 예상)을 계산해
  연금저축 600만·합산 900만 한도의 초과분과 IRP 남은 한도, 환급 증가액(13.2%)을 제안으로 낸다. 내년 월 배분안도 제시.
- 해외주식: 미국 상장 보유분의 평가손익(현재 환율 근사)으로 연 250만 원 기본공제 안의 이익 실현·재매수 효과(22%)를 계산.
- ISA 미보유 시 개설 제안(3년, 200만 원 비과세, 만기 연금 이전 추가 공제).
- 규칙 메모: 혼인신고 시점(현재 각자 1주택 → 신고 후 1세대 2주택, 혼인 합가 특례 10년, 규제지역 다주택 대출 제한),
  고가주택(12억 초과분 과세, 취득일·취득가 필요), 혼인 증여공제(전후 2년 1억 추가), 혼인세액공제(50만 원), 저축성 보험
  10년 유지, 금융소득 2천만 원.
- 납세자 단위: 연금·해외주식·ISA 계산은 `owner_id = "self"` 레코드만 쓴다(배우자 계좌는 합치지 않는다).
- 근거: 규칙마다 공식 출처(법령정보센터·국세청)를 달고 보고서 세금 절 아래에 "세법 기준 연도·확인일"과 함께 표시한다.
  서술 단계는 이 계산을 참조 `tax`로 인용한다.
- 연말정산 점검표(10~12월은 두 판 모두): 연금저축·IRP·보장성 보험료·카드.
- 주택 양도세 추정: 로컬 `[properties]`의 취득 연도·취득가와 원장 평가액으로 누진세율(2026년)·장기보유특별공제·기본공제를
  반영해 계산한다(필요경비 제외). 거주 주택은 1세대 1주택 고가주택 기준, 배우자 주택은 2년 거주 여부 두 경우를 함께 보인다.
- 은퇴 궤도: 로컬 `[household]`의 출생 연도와 은퇴 후 월 생활비(현재 가치)로 필요 자금(연 생활비 ÷ 인출률 4%)과 연금 계좌만의
  준비율(실질 3%, 현재 적립 유지)을 55·60·65세로 보인다. 국민연금·퇴직금·부동산은 제외. 환율이 없어 원화로 바꾸지
  못한 연금 자산·납입은 0으로 두지 않고 건수를 세어, 비율을 "확인된 금액만으로 본 하한"이라고 밝힌다.
- 위험 성향: `[advice] risk_preference`(conservative·balanced·growth·growth_aggressive)를 검증해 서술 단계의
  `household_profile`로 넘긴다. 방향·순서는 성향을 따르되 더 안전한 대안과 날짜가 정해진 자금 수요는 빼지 않는다.
- 로컬 `[household]`(Git 제외): 출생 연도, 은퇴 생활비, 혼인신고 여부, 동거 여부, 세전 기본 연봉(`annual_gross_salary`,
  성과급·주식 보상 제외). 서술 단계에는 나이와 혼인신고 여부만 넘긴다. 연봉은 넘기지 않고 예정 소득의 세금 추정에만 쓴다.
- 예정 소득(FR-20, `src/smith/future_income.py`): cashflow `bonus`·`stock_compensation`을 확실성별로 평가(주식은 같은 종목의
  최신 보유 단가, 세전은 근로소득 증가분 세금·보험 차감)하고, 주택 계산(`cases.home_facts`)은 시나리오별 확실성 규칙으로
  "예정 소득 포함" 값을 따로 더한다. 순자산·월 현금흐름·준비 상태·주식 단계적 전환·보증금 반환 계산에는 넣지 않는다.
  `smith advise`는 `--config`의 `[household] annual_gross_salary`를 읽는다. 자세한 규칙은 `docs/report-design.md` §15.
- 로컬 `[properties."record-id"]`(Git 제외): 공식 실거래가 매칭용 시군구 코드·법정동·단지 키워드. 동·호수는 저장하지 않으며
  모델·웹 조사로 보내지 않는다. 키는 `smith realestate login`(OS 자격 증명 저장소).

## 공식 부동산 데이터 (`src/smith/realestate.py`, 원장 v13 `property_deals`)

- 국토교통부 아파트 매매·전월세 실거래가(공공데이터포털, `smith realestate login`으로 키 저장)를 시군구·월 단위로 받아
  로컬 `[properties]`의 단지명(정확한 MOLIT 이름)·법정동·전용면적(±1㎡)이 맞는 거래만 저장한다. 동·호수는 저장하지 않는다.
  같은 날·층·금액·면적의 계약은 한 행으로 묶고 `active_count`·`cancelled_count`로 건수를 센다(동 번호를 저장하지 않기 때문).
- 동기화는 받아 온 (주택, 종류, 월) 단위로 **그 달 전체를 교체**한다. 신고 취소·해제가 다음 동기화에 반영되고, 설정에서
  빠진 주택의 거래는 지운다. 기본 13개월(6개월 비교에 앞선 1개월 여유).
- 분석: 최근 6개월 매매 중간값(해제 거래 제외)과 그 이전 6개월 대비 변화(양쪽 모두 3건 이상일 때만), 최근 6개월 순수
  전세(월세 0) 중간값·범위. 3건 미만이면 보고서와 제안에 "참고용"으로 표시하고 역전세 차액은 계산하지 않는다.
- 상품 검토(`smith.picks`, report design §26): 제안이 옮기라는 상품을 코드가 지휘하는 네 번의 headless 호출(scout·verify는 웹 도구,
  critique·select는 도구 없음)로 고르고 검증해 `product_reviews`에 저장한다. 모델은 가구 금액을 보지 않으며(select만 비식별 맥락),
  보고서와 메일 답장은 저장된 검토를 읽는다(재구축은 그 시점 이전 검토만). 검증의 match는 공식 호스트 허용 목록 안의 페이지에서만
  인정되고, 가격은 코드가 숫자·통화·날짜를 대조하며, 1순위는 코드 규칙(비용·세금 경로·보유·연속성)이 정한다. 검토는 회차 2~4시간 전
  창에서만 돌고 발송 경로에서는 돌지 않는다.
- 설정 검증: `[properties]`의 형식 오류는 `load_config`가 필드 이름과 함께 거부한다.
- `[properties."record-id"] lease_exit`(선택, `relet` 기본 | `sell`): 그 집의 전세보증금을 어떻게 돌려줄 계획인지. `sell`이면 만기 매도가
  보증금 반환의 기본 경로가 되고(`lease.plans` default `sale`), 제안·전략 궤도·주식→안전자산 이동·스트레스 테스트가 그 계획을 따른다
  (고객 메일 2026-10-19, report design §24).
- `[properties."record-id"] residence_years`(선택, 정수): 소유자 세대가 그 집에 거주한 연수. 2년 이상이고 2년 이상 보유했으면 양도세를
  1세대 1주택 비과세 기준으로 계산해 보고서의 기준 숫자로 쓰고, 일반 과세는 "요건 미충족 시"로 옆에 둔다(고객 메일 2026-10-21).
  보고서 부동산 절은 원장 평가액과 실거래 추정의 차이를 보이고 갱신 여부는 고객이 정한다. 보증금 반환 제안은 담보 주택의
  전세 중간값으로 역전세 부족분을 계산한다. 서술 단계에는 단지명 없이 별칭별 수치만 넘긴다.
- 발행 시 동기화하고(`sync_runs` source `molit`), 실패하면 보고서 안내에 적는다. R-ONE 키는 저장만 해 두었다(미사용).

## 메일 질의응답 (FR-18, `src/smith/qa.py`, 원장 v13·v16 `mail_questions`)

- 사용: `smith mail login --client-file … --read`(읽기 권한 추가, 개인용 미검증 앱 경고 화면이 나옴) 후 로컬 설정
  `[mail] answer_replies = true`. 정기 작업이 15분마다 확인하고, 수동은 `smith mail answer`.
- 비용·노출: 최근 30일 Smith가 보낸 보고서 스레드만 읽는다(메일함 목록 조회 없음). Gmail 읽기는 제한된 함수
  (`thread_of`, `thread_headers`, `message_body`)만 쓴다. 스레드는 머리글(`format=metadata`)만 먼저 읽고, 본문은
  질문으로 인정된 메일만 받는다. 모델은 실제 질문이 있을 때만 부르며 하루 최대 10건(선점과 같은 트랜잭션에서 센다).
  질문은 계정 소유자가 보낸 메일(SENT 표지)이면서 설정된 주소에서 온 것만 인정한다. Smith가 보낸 메일은 모두
  `X-Smith-Message` 머리글을 달아, 메시지 ID를 모르는 Smith 답장도 질문으로 오인하지 않는다. 그 밖의 메일은 `skipped`로
  기록해 다시 보지 않는다. 인용된 원문은 잘라 낸다.
- 질문한 보고서 기준: 질문은 그 보고서 스레드의 `report_id`로 묶인다. 답변 데이터는 그 보고서의 계보(`as_of`·
  `known_at`)로 원장에서 다시 만들고(이력 원장이라 재현됨), 그 보고서에 쓴 브리프와 서술(감사 run ID)을 그대로 쓴다.
  보고서 이후 원장이 갱신되었으면 "이 답은 MM월 DD일 보고서 시점의 원장 기준" 메모를 코드가 붙인다. 계보가 없는
  v14 이전 보고서는 보고서 생성 시각과 같은 시각의 서술을 찾는다.
- 답변: 보고서와 같은 입력(원장 맥락·제안·세금·실거래·브리프)과 그 보고서의 서술 판단, 고객 질문(식별자 가림)을 받는다.
  서술과 같은 코드 검증, 실패 시 1회 수정, 그래도 남는 문제는 답을 버리지 않고 "자동 점검 메모"를 붙여 보낸다.
  고객이 말한 금액(이번 질문, 앞선 발언, 고객 기억; "원" 없는 "21억"도) 중 원장에 없는 값은 답에 쓰여도 "말씀하신
  수치(…)는 원장에서 확인되지 않은 값"이라고 밝힌다.
  답은 대화형으로 짧게 쓴다(결론 1~2문장 + 근거 3~5문장, 400~700자 목표, 최대 1,500자). 실행·송금·수신자 변경
  요청은 거절하고 분석만 제공한다.
- 공개 정보 조회(FR-43, `src/smith/qa_lookup.py`, `mail-answer-v15`·`mail-lookup-v1`): 첫 답변 호출이 출력 `lookup`으로
  조회가 필요하다고 하면(답은 한 줄로 두고) 코드가 판정한다. 보유 종목 조회는 `lookup_candidates`(의견 키·공개 이름·시장)의
  종목과 고정 주제(`dividend`·`earnings`·`disclosure`·`news`)만 받고, 조회 입력은 코드가 공개 이름·종목코드·시장으로 쓴다(앞
  다섯 자리가 같은 KR 상장 주식은 같은 회사의 다른 주식으로 함께 묻는다). 공개 주제는 코드 목록(`PUBLIC_SUBJECTS`: 금리·대출
  규제·주택 세제·금융소득 과세·연금 세제·환율·증시, 그리고 그 보고서의 T* 조사 주제)의 키 하나만 받는다. 모델이 쓴 검색어는
  받지 않는다(2026-10-29 리뷰: "연봉 7천만원 맞벌이 양도세" 같은 자유 검색어는 어떤 패턴으로도 가구 사실을 다 막지 못한다). 조회 호출은
  `WebSearch,WebFetch`만 쓰고 가구 데이터를 받지 않는다(`advice_runs` `mail-lookup`). 결과는 `sources.verify`로 URL·숫자를
  대조해 보고서 브리프 뒤 번호(R<n+1>…)로 붙고, 배당은 인용한 결과가 모순(`mismatch`)이 아니고 그 1주당 금액을 적었으며, 페이지를
  읽었다면 페이지 숫자(`sources.check`의 `found`)에도 그 금액이 있을 때만 채택한다(날짜만 맞은 `matched`는 금액의 증거가 아니다).
  금액은 결과 문장에서 "주당"·"per share" 바로 뒤에 돈으로 쓰인 것만 인정하고(날짜의 "30"은 금액이 아니다), 한 페이지의 결과가
  여럿이면 각각을 따로 본다. 기준일·지급일은 그 결과 문장에 쓰인 날짜만 쓰고 아니면 모름으로 둔다(기준일을 모르면 보고서 수량).
  보고된 배당을 증명하지 못한 주식이 있으면 합계를 내지 않는다. 페이지를 읽지 못한 배당은 메모를 붙여 쓴다. 받을 배당은 `qa_lookup.estimates`가 계산한다: 배당 기준일 원장(보고서의 `known_at` 기준)의 보유 수량, 그날 기록이
  없거나 기준일이 보고서 뒤면 보고서 수량(`quantity_basis`), 계좌 종류별 세전·원천징수·세후(일반: 14%와 그 10%, 각 10원 미만 절사;
  ISA·연금: 0)를 보유분(계좌)마다 계산해 소유자·계좌 종류별로 합친다. Hermes 운용분은 빼고, 수량이 없거나 통화가 다른 보유분이
  있으면 `uncounted_lots`로 세고 합계를 내지 않는다. 두 번째 답변 호출(`mail-answer-looked-up`)이 `lookup`·`dividend_estimates`를 받아 쓰고, 그
  수치는 코드 산출물이라 근거로 인정된다(`narrative._EVIDENCE_KEYS`). 대조하지 못한 공시 숫자, 보고서 수량 사용, Hermes 제외,
  세금 미계산은 코드가 메모로 붙인다. 조회가 거절·실패해도 두 번째 호출이 그 사실을 밝히며 답한다.
- 전자공시(OpenDART, `src/smith/dart.py`, 키는 OS 자격 증명 저장소 `smith.dart`, 2026-10-29 공식 안내서와 실제 응답으로 확인):
  국내 보유 종목 조회는 웹보다 먼저 전자공시를 본다. `corpCode.xml`(종목코드→고유번호, 우선주는 앞 다섯 자리의 보통주로 찾음, 원장
  옆 `data/dart/corp_codes.json`에 7일 보관), `list.json`(접수일 구간의 공시 목록, `013`은 없음), `document.xml`(원문 zip). 배당
  질문은 최근 120일 안의 가장 새 '배당결정' 공시(정정 공시가 이김) 원문의 고정 양식(배당구분, 1주당 배당금 보통주식·종류주식,
  배당기준일, 지급 예정일자, 이사회결의일)을 코드가 읽어 공식 출처 항목 하나와 배당 수치로 만들고, 웹 호출 없이 두 번째 답변 호출로
  간다. 종류주식이 여럿이고 금액이 다르면 우선주 금액은 비워 둔다(어느 종류인지 추측하지 않음). 다른 주제는 최근 30일 공시 제목
  5개를 웹 결과 앞에 붙인다. 키 없음·호출 실패·배당 결정 없음은 웹 조사로 넘어가고 그 사유를 `gaps`에 남긴다. 키는 쿼리 문자열에만
  실리고 오류·로그·모델 입력에 들어가지 않으며(`all_secrets`에 포함되어 외부 전송 검사가 막는다), 리다이렉트는 따르지 않는다.
- 이어지는 대화(원장 v16): 질문 원문(식별자 가림, 모델에 보낸 그대로)은 선점할 때, 보내는 답(메일 본문 텍스트)은
  `sending` 직전에 `mail_questions`에 저장한다. 같은 스레드의 새 질문에는 그보다 앞선 질문·답 최근 6턴을 오래된 순으로
  `conversation`(`client`·`smith`)에 담아 보낸다. 대화 이력의 기준은 Gmail 인용문이 아니라 원장이다(인용은 계속 잘라
  낸다). `smith`에는 발송이 확인된(`answered`) 답만 넣고, 답하지 못했거나 결과 미상이면 `null`이다. 한 번의 확인에서 같은
  스레드 질문이 여러 개면 받은 순서대로 처리해 뒤 질문이 앞 답을 본다. 검증: 앞선 고객 발언 속 수치는 지금 질문과 같이
  다뤄 "말씀하신 수치" 메모를 붙이고, Smith의 이전 답 속 수치는 근거로 인정하지 않는다(검증되지 않은 수치가
  반복으로 근거가 되지 않게). v16 이전 답은 같은 선점 시각의 감사 기록(`advice_runs`)으로 한 건이 특정될 때만 채운다
  (가장 나중의 성공 출력 = 보낸 답, 메모·출처는 빠짐). 특정 조건: 그 시각에 건너뛰지 않은 질문이 정확히 1건이고, 그
  시각의 `mail-answer` 입력 속 질문도 1종일 것. 한 번의 확인에서 질문들은 선점 시각을 공유하고, 실패한 질문도 모델을
  불렀을 수 있으며, 재시도된 질문은 옛 시각에 실행 기록을 남기기 때문이다(2026-10-07 리뷰: 처음 조건은 `answered`만
  세어 다른 질문의 답을 붙일 수 있었다). 운영 원장은 이미 v16이었으나, 채워진 4건 모두 강화된 조건을 만족함을 확인해
  별도 교정 이전은 두지 않았다.
- 상태: `answering`(선점) → `sending`(발송 직전 커밋) → `answered`·`failed`·`unknown`. 명확한 실패(`failed`)는 다음
  실행에서 최대 3회 다시 시도하고, 결과 미상(`unknown`)은 다시 보내지 않는다. 60분 넘게 멈춘 `answering`은 `failed`,
  `sending`은 `unknown`으로 복구한다(조회가 붙은 답은 호출 네 번까지 길어질 수 있어 2026-10-29 30분에서 늘림; 정기 작업은
  `IgnoreNew`로 겹치지 않고, 이 임대 시간은 수동 실행과의 겹침을 막는다). 같은 스레드에 `In-Reply-To`·`References`와 `threadId`로 답한다. 모든 호출은
  `advice_runs`(`mail-answer`)에 기록한다.
- 시간대: 답변용 보고서 데이터는 설정의 시간대로 만든다(미리보기도 설정 시간대를 쓰며, 설정 파일이 있는데 깨져
  있으면 기본값으로 넘어가지 않고 오류로 멈춘다).
- 질의응답 처리 실패는 보고서 발행을 막지 않는다. 정기 작업은 답변 결과와 실패 코드(예: 읽기 권한 없음, 토큰 만료)를
  `report-runs.log`에 남긴다.

- 저장: 원장 옆 `data/memory/<주제>.md`(Git 제외, 원장과 같은 보호 규칙). 주제는 `profile`(가구·인적 사항),
  `property`(부동산·주거), `plan`(계획·일정), `preference`(선호·원칙), `other`. 줄 하나가 사실 하나이고
  `- YYYY-MM-DD · 출처 · 내용` 형식이다. 사람이 직접 쓴 `- 내용` 줄도 읽으며(날짜 없음, 출처 "직접 작성"), 주제가 아닌
  파일 이름은 `other`로 본다. 들여 쓴 줄과 본문 문장은 읽지 않는다. 고치거나 지우려면 파일을 편집한다.
- 쌓이는 경로(고객 본인만):
  - 메일 답변: 출력 `remember`(최대 3개, 주제와 한 문장)로 이번 메일에서 고객이 말한 사실을 뽑는다. 이미 있는 것은 빼고
    답장에 "기억해 두겠습니다"로 보여 주며, 답장이 `answered` 또는 `unknown`(도착했을 수 있음)이 된 뒤 메일 날짜로
    저장한다. 명확한 실패는 다시 시도할 때 저장한다. 저장 실패는 답변을 취소하지 않고 실행 결과에 남긴다.
  - 대화: `smith memory add 주제 "내용" [--source 대화]`. 개발 대화에서 사용자가 알려 준 정보도 이 명령으로 넣는다.
  - 웹 조사 결과는 기억이 되지 않고, 조사 모델은 기억을 받지 않는다.
- 정리: 쓸 때와 읽을 때 모두 식별자(전화·이메일·계좌 등)를 가리고 동·호수 번호를 지운다("(동·호 생략)"), 한 줄 300자.
  같은 내용(공백·문장부호 차이 무시)은 다시 쓰지 않는다. 바로잡은 내용은 새 줄로 쌓이고 "새 내용이 이긴다"고 지시한다.
- 검색(가벼운 RAG, 임베딩 없음): 모든 기억이 4,000자 안이면 전부, 넘으면 `profile`·`preference`는 항상, 나머지는 호출
  텍스트(메일 질문·이전 턴, 보고서의 제안·전략·판단 불가 주제, 자문 질문)와 겹치는 글자 2개 묶음의 희소도 가중 점수와
  최신순으로 고른다. 외부 임베딩 API를 쓰지 않아 기억이 색인을 위해 밖으로 나가지 않고, 조사가 붙은 한국어도 맞춘다
  ("푸른마을을" ↔ "푸른마을아파트"). `smith memory search "질문"`으로 무엇이 전달될지 미리 본다.
- 전달: 보고서 서술(단일·팀 모두, 상태에 저장·전달 개수), 메일 답변, `smith advise`의 입력에 `client_memory`로 넣는다.
  프롬프트는 "고객의 말이지 원장 사실이 아니고, 새 것이 이기며, 원장 수치를 덮지 않는다, 기대면 고객님 말씀 기준이라고
  밝힌다"로 다룬다. 기억 속 수치는 고객 질문 속 수치처럼 근거로 인정하되, 메일 답변에서는 "말씀하신 수치" 메모를 붙인다.
  기억 폴더를 읽지 못하면 기억 없이 진행하고 상태에 남긴다.

## 메일 발송 (6단계, `src/smith/gmail.py`)

Gmail API, 기본 권한은 `gmail.send` 하나. 질의응답을 켜면 `--read`로 `gmail.readonly`를 더하지만 코드는 Smith 보고서
스레드를 읽는 제한된 함수만 쓴다. 2026-10-04 공식 문서로 확인.
- 로그인: 데스크톱 앱 OAuth, 루프백(`http://127.0.0.1:<임의 포트>`) + PKCE(S256) + state 검사, `access_type=offline`.
  OAuth 앱은 프로덕션 게시 상태여야 한다(테스트 상태는 refresh token이 7일 후 만료).
- client ID·secret·refresh token은 OS 자격 증명 저장소(`smith.gmail`)에만 둔다. 다운로드한 client JSON은 로그인 후 삭제해도 된다.
- 받는 주소는 Git 제외 `config/smith.local.toml`의 `[mail] recipient` 하나뿐이다. 모델 출력이나 보고서 내용이 수신자를 바꿀 수 없다.
- 발송 결과: 성공(메시지 ID), 실패(4xx), **결과 미상**(요청 후 응답 유실, 5xx, 또는 성공 상태인데 본문·메시지 ID가
  없는 경우). 결과 미상은 자동 재발송하지 않는다. `sent`는 받은편지함 도착 확인이 아니라 Gmail API가 Message를
  반환했다는 뜻이다.

## PB 기준 보강 (report-design §16, `src/smith/stress.py`, `proposals.spending_room`)

- 복합 스트레스 테스트(`stress.test`): 원장 뷰·KPI·분야 지표만으로 결정적으로 계산한다. 가정값(금리 +1.5%p, 가장 큰 근로·사업

  상한을 두고, 환산하지 못한 금액이 있으면 해당 수치와 판정은 `None`/`unknown`, 순자산 하락률은 재무상태표가 완전하고 순자산이
  양수일 때만 낸다. 판정은 유동성 판정(`liquidity_verdict`)과 의무 표지(`flags`, 가까운 보증금 미충족)로 나뉘고 종합 `verdict`는
  표지가 있으면 최소 `watch`다. `build_report`가 `data["stress"]`로 넣고, 서술 입력 `sector_metrics.stress`(허용 근거), 생활판
  전체 섹션·종합판 한 문단 요약, 상태 배지(`fragile` 또는 보증금 표지 → 최소 주의)가 쓴다. 멈출 수 있는 지출은
  `cases.monthly_outflow`(공개 함수로 바꿈)로 센다.
- 부동산 LTV의 분자는 `report_data.SECURED_LOAN_CATEGORIES`(`mortgage`)만이다. 그 집을 담보로 적은 다른 채무(전세보증금 반환
  의무 등)는 `debt`(관련 부채 합계)와 `deposits`에 남고 비율에는 들어가지 않는다(1차 리뷰 2026-10-17).
- 안심 소비 한도(`proposals.spending_room`): 제안 규칙 `spending-room`과 생활판 섹션이 같은 계산을 쓴다. 약정 기준(`room`: 비상금과
  가장 가까운 보증금)과 계획한 목표까지 지킬 때(`room_with_goals`: 주택 계획이 이미 저축한다고 가정한 월 순현금흐름
  `home_progress.monthly_net_self`·`months`와 다른 날짜 목표의 전액 적립)의 두 숫자다. 입력 미상, 환산 못 한 목표, 계산 못 한
  주택 계획이면 미결 판단. 12개월 안 보증금을 지금 속도로 못 모으면 우선순위 1.
- 또래 벤치마크: `research.topics`의 `benchmark` 범주. 그 범주를 조사 목록에 둔 판(종합판)에만 생기고, 원래의 전체 월요판·목요판과
  `smith research topics` 목록(전체 집합)에는 들어가지 않는다. 질문은 연령대 일반이라 가구 정보가 검색어에 들어가지 않으며,
  고객 나이는 서술 단계(`household_profile.age`)에서만 쓴다.
- 심리 함정 브리핑: 자문(`advice-v7`)·메일 답변(`mail-answer-v8`) 시스템 프롬프트의 지침이다. 출력 스키마는 바뀌지 않았고, 서술

## 정기 발행 (6단계, `src/smith/delivery.py`, 원장 v8~ `report_runs`)

- 회차: 설정의 요일·시각·시간대(기본 월·목 06:00 Asia/Seoul). 회차마다 행 하나(slot 유일).
- 시간대: 계산의 날짜(현금흐름 시작·종료일, 목표일, 제목 날짜)는 설정 시간대의 `as_of`에서 얻는다.
  월요일 06:00 KST는 UTC로 일요일이므로, 발행·미리보기·자문·요약 모두 현지 시각으로 바꿔 넘긴다. 저장은 UTC.
- 상태 흐름: `building`(선점, 메일 요청 전) → `sending`(요청 직전 커밋) → `sent`·`failed`·`unknown`.
  `sent`·`unknown`·진행 중 회차는 자동으로 다시 보내지 않고, `failed`(명확한 실패)만 최대 3회 재시도한다.
  수동 발행(`send-now`)은 회차를 소모하지 않는다.
- 중단 복구: 30분 넘게 `building`인 실행은 메일 요청 전이므로 `failed`(재시도 가능), `sending`인 실행은 이미
  전달됐을 수 있으므로 `unknown`(자동 재발송 금지)으로 닫는다. `run-due`가 매번 먼저 정리한다. v7에서 넘어와
  `send_started_at`이 없는 `sending` 행은 선점 시각을 대신 쓴다.
- 선점 확인(fencing): `building` → `sending` 전환은 그 실행의 `report_id`이고 아직 `building`일 때만 성공한다.
  임대 시간이 지나 복구되었거나 새 실행이 같은 회차를 다시 선점했다면 전환이 0건이 되고, 이전 실행은 메일을
  보내지 않고 끝난다(`claim-lost`).
- PC가 꺼져 회차를 놓치면 다음 실행에서 최신 회차 한 통으로 보내며, 제목에 "지연 발송", 본문에 놓친 회차를
  표시한다. 놓친 회차는 그 보고가 `sent` 또는 `unknown`으로 끝날 때 같은 트랜잭션에서 `merged`로 기록한다.
  명확히 실패하면 놓친 회차는 재시도에 그대로 남는다. 최초 실행은 과거 회차를 소급하지 않는다.
- 이전 회차가 실패한 채(재시도가 남았든 아니든) 다음 회차가 오면, 그 회차도 놓친 회차로 다음 보고서에 합치고
  발송되면 `merged`로 바꾼다. 결과 미상 회차와 발행 전 동기화 실패는 다음 보고서 상단 안내에 적는다.
  `report status`도 중단·미상 상태를 표시한다.
- 계산 정밀도: Decimal 정책은 하나다. `smith/__init__.py`가 패키지를 불러올 때 기본·현재 문맥을 100자리로 정해,
  계산·반올림(`quantize`)·직렬화·표시와 스레드 모두 같은 정밀도를 쓴다. 입력 값은 정수 15자리·소수 8자리이므로
  금액×환율(약 30자리), 수량×가격×환율도 반올림되거나 `InvalidOperation`이 나지 않는다(최대값 경로 테스트).
- 한 스냅샷: `build_report` 전체가 읽기 트랜잭션 하나에서 돈다. 작성 중 import가 들어와도 KPI·변동 분석·제안이
  서로 다른 원장 상태를 보지 않는다(쓰는 쪽은 보고서 데이터 작성이 끝날 때까지 기다린다).

  출발점(`restated_start`)부터의 변화를 보이고, 정정액(`correction`)은 본문과 표에 "합계 제외"로 따로 적는다.

  보내며, 금액 없는 경고를 로그에 남긴다.
- Hermes 운용 자산(`managed_by=hermes`): Smith가 매각·변경을 권하지 않으므로 쓸 수 있는 돈으로 세지 않는다.

- 토스 예수금: API가 매수 가능 금액만 주므로 현금·유동성 절과 데이터 상태에 "미수집"을 밝히고, 수동 입력한 증권

- 비교 기준은 직전 `sent` 보고의 스냅샷 시각이다. 발송 직전에 토스·근거 동기화를 실행하고 반환 코드를 확인한다
  (토스 자격 증명이 없어도 `sync_runs`에 실패를 남긴다). 정기 동기화는 `--close-missing`으로 실행해 스냅샷에서
  사라진 종목(매도)을 종료한다. 성공한 스냅샷은 모든 요청이 성공하고 형식이 맞아야 만들어지므로 완전하다. 이 옵션이
  없던 때는 종목 하나를 전부 팔면 이후 모든 동기화가 거부되어 보유 내역 전체가 갱신을 멈췄다. 다만 보유 종목이
  0개인 응답은 공급자 오류일 수 있어 거부하고(`empty-snapshot`), 실제로 모두 팔았다면 `--allow-empty`로 직접 반영한다.
- 일정 변경(원장 v15 `schedule_state`): 회차는 매번 현재 설정으로 다시 계산하므로, 그대로 두면 이미 보고한 날의
  시각을 늦추거나 지난 요일을 추가할 때 "놓친 회차"로 오인해 중복·지연 보고를 보냈다. `run-due`는 설정의 요일·

  표시(`schedule-changed`)해 변경 이전 회차는 보내지 않는다. 새 일정은 변경을 처음 본 정기 실행 이후 회차부터
  적용되며, 그 사이 꼭 받아야 할 보고는 `report send-now`로 보낸다. 최초 실행은 현재 일정을 기록만 한다.
- 백업: `smith backup [--out DIR] [--keep N]`이 읽기 전용 연결에서 SQLite 온라인 백업으로 일관된 사본을 만들고
  `PRAGMA integrity_check`를 통과한 사본만 `smith-<UTC 시각>.db` 이름으로 남긴다(통과 전에는 임시 이름). 같은

  돌지 않을 때 사본을 `data/smith.db`로 복사한다.
- 실행: Windows 작업 스케줄러가 로그온 상태에서 15분마다 `pythonw -m smith report run-due`를 호출한다(자격 증명

## 권한 경계

금융 API 키는 어댑터만 접근한다. 조회 전용 권한을 공급자가 지원하면 우선 사용하고,
미지원이면 명시적으로 허용한 조회 endpoint만 어댑터에서 호출한다.
인증 token 발급의 POST와 주문 POST를 혼동하지 않는다. 주문 기능 자체는 제공하지 않는다.
토스증권 Open API는 scope가 없어 같은 token으로 주문 API도 호출된다. 따라서 토스 어댑터는
`docs/toss-openapi.md`의 허용 목록 밖 요청을 네트워크 호출 전에 거부하고, 이를 테스트로 검증한다.

Claude Code headless 실행은 비밀정보나 운영 DB에 직접 접근할 수 없는 별도 작업 경계에서
수행한다. 범용 shell과 임의 HTTP를 자문 도구로 노출하지 않는다. 실제 CLI 버전의 권한·도구
제한 방식을 공식 문서로 확인한다. `--dangerously-skip-permissions`를 기본값으로 삼지 않는다.
Claude Code에서 Smith 기능을 호출하는 경로와 Smith가 headless 추론을 호출하는 경로를
분리해 자기 자신을 재귀 호출하지 않도록 한다.

LLM이 작성한 텍스트는 발송 대상·스케줄·금융 API 호출을 변경할 수 없다.
메일 수신자는 신뢰된 로컬 설정에서만 읽는다. 로그에는 잔고 원문과 인증정보를 남기지 않는다.

## 스케줄 및 복구

시간대 인식 스케줄러가 설정된 현지 요일·시각을 해석한다. 호스트 로컬 시간대에 의존하지 않는다.
지정 발행 슬롯/요청 ID, 데이터 snapshot ID, 분석 버전, 발송 상태를 저장한다.
수동 보고는 정기 보고의 슬롯을 소모하지 않는다. 재시작 후 놓친 회차와 일정 변경의 처리는 위 "정기 발행"에 있다.
`enabled=false`가 예시 기본값이다. 실제 설정과 발송 테스트를 완료한 뒤 명시적으로 활성화한다.

## Hermes 후속 연동

초기 계약 후보: portfolio snapshot, positions, cash, trades, performance, strategy explanation.
계좌의 사실과 전략 설명을 분리하고 source account mapping으로 중복을 제거한다.
연동 전까지 Hermes 운용 계좌는 수동 입력으로 관리하며, 연동 시 그 수동 레코드를 종료하고 API 원천으로 대체한다.
수집 시점, 스키마 버전, 부분 실패, 인증을 정의한다. 명령/주문 endpoint와 DB 직접 공유는 피한다.
현재 Hermes API의 경로·구조·인증은 확인하지 않았으며 임의로 고정하지 않는다.
