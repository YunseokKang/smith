# 승인형 주문 실행 설계 (토스증권)

상태: **승인됨·1단계 구현** (사용자 결정 2026-10-30, FR-47). 실계좌 주문은 아직 한 번도 나가지 않았다(§10의 2단계 전).
`docs/requirements.md` §1·§7, `AGENTS.md` "Financial Execution Boundary", `CLAUDE.md`의 경계 문장을 같은 변경에서 고쳤다.

계기: 2026-10-30 세금판 레터가 셀레스티카(CLS) 10주를 전부 팔고 다시 사서 해외주식 양도소득 기본공제
250만 원 안에서 평가이익(보고서 기준 약 241만 원)을 실현하자고 제안했다. 사용자는 이런 제안을 메일이나 대화로
지시하면 Smith가 실행하되, 실행 전에 계획을 보고하고 최종 승인을 받은 뒤 진행하기를 원한다.

## 1. 한 줄 요약

**사람이 시작하고, 코드가 계획하고, 사람이 휴대폰으로 승인하고, 코드가 실행 직전에 다시 확인한 뒤 주문한다.**
LLM은 주문 경로 어디에도 없다. 모델은 자연어 요청을 초안으로 바꾸는 데만 쓰이고, 그 초안은 코드가 검증한다.

## 2. 범위

1단계에서 하는 것
- 토스증권 본인 종합매매(`BROKERAGE`) 계좌 하나, 국내·미국 상장 주식·ETF의 **현금 매수·매도**.
- **지정가(`LIMIT`) + 당일(`DAY`)** 주문, 정규장 안에서만. 미체결분은 장 마감에 자동 취소된다(토스 명세).
- 다리(leg) 여러 개의 계획: 예) 매도 체결 확인 → 재매수. 다리 순서는 코드가 강제한다.
- 미체결 주문의 **취소**(Smith가 낸 주문만).

1단계에서 하지 않는 것 (코드 허용 목록 밖, 네트워크 전에 거부)
- 시장가·금액 기준·소수점 주문, 장전·장후·시가·종가 주문, 정정(`modify`), 조건주문 전체.
- 신용·미수, 1억 원 이상 주문(`confirmHighValueOrder`는 항상 `false`로 보낸다).
- 한국투자증권·Hermes 계좌, 연금·ISA 계좌, 송금·이체·환전·대출·보험·상품 가입.
- 모델이나 보고서가 스스로 시작하는 거래, 반복·자동 매매. 보고서는 제안만 하고, 거래는 고객의 요청으로만 시작한다.

## 3. 위협과 대응

| 위협 | 예 | 대응 |
|---|---|---|
| 프롬프트 주입 | 조사 페이지·공시·메일 본문이 "전부 팔아라"라고 씀 | 주문 실행 모듈은 LLM이 부를 수 없다. 거래는 고객 발언으로만 시작하고, 모델 초안은 코드가 보유·한도와 대조한다 |
| 승인 위조 | 같은 Gmail 계정에 붙은 다른 앱·에이전트(Claude Gmail 커넥터 등)가 "OK" 답장을 보냄 | 승인에 **휴대폰 인증 앱의 6자리 일회용 코드(TOTP)** 를 요구한다. 메일에 쓰인 어떤 값으로도 승인할 수 없다. 고객이 다른 메일에 보낸 코드를 옮겨 붙이는 것은 보낸 메일 검색으로 막는다(§5, 계정 완전 장악 시의 남는 위험 포함) |
| Gmail 계정 탈취 | 공격자가 본인 계정으로 답장 | 위와 같음(코드는 휴대폰에만 있다) + 1회·1일 금액 한도 |
| 오래된 승인 | 아침에 승인한 계획이 가격이 바뀐 오후에 실행 | 계획 만료(기본 60분) + 실행 직전 가격·보유 재확인, 허용 폭 밖이면 중단 후 재제안 |
| 중복 주문 | 시간 초과 뒤 재시도로 두 번 매도 | 다리마다 고정 `clientOrderId`(토스 멱등키, 10분 유효). 10분이 지나면 재전송하지 않고 주문 목록으로 대조 |
| 응답 유실 | 주문이 접수됐는데 응답이 끊김 | 상태 `unknown`으로 기록하고 다음 단계로 가지 않는다. 같은 키 재요청 또는 주문 목록 대조로만 확정 |
| 반쪽 실행 | 매도는 체결, 재매수는 실패 | 즉시 `[Smith][거래]` 메일로 "현금으로 남아 있음"을 알리고 재매수는 새 승인을 받는다 |
| 개발 에이전트 오용 | 개발 세션(Claude Code)이 실수로 주문 | 개발 세션도 계획 생성까지만 할 수 있다. 승인은 휴대폰 코드가 있어야 하고 실행은 스케줄러의 실행 단계만 한다 |
| 설정·키 노출 | 로그·모델 입력에 키나 계좌번호 | 기존 규칙 그대로. 주문 응답 원문은 로그에 남기지 않고 원장에 필요한 필드만 저장 |
| 같은 PC의 다른 프로그램 | 같은 Windows 사용자로 도는 악성 코드·에이전트가 자격 증명 저장소를 읽음 | **막지 못한다.** 토스 키 자체가 같은 저장소에 있어 그런 프로그램은 Smith 없이도 주문할 수 있다. 인증 앱 코드는 메일 쪽 위조를 막는 장치이고 PC 안의 경계는 기존과 같다. 개발 에이전트에는 CLAUDE.md로 승인·등록·비밀 읽기를 금지했다 |

## 4. 모듈 구조

기존 조회 전용 `toss.py`의 허용 목록은 **바꾸지 않는다**. 주문은 별도 모듈이 맡아 경계를 코드와 테스트로 분리한다.

| 모듈 | 책임 | 네트워크 |
|---|---|---|
| `trade_intent.py` | 거래 의도·계획·다리의 데이터 형식과 순수 검증(심볼, 수량 정수, 가격 호가 단위, 한도, 다리 순서) | 없음 |
| `trade_plan.py` | 사전 점검으로 계획서를 만든다: 보유·매도 가능 수량, 매수 가능 금액, 현재가·호가, 상·하한가, 매수 유의사항, 수수료, 휴장일, 세금 추정 | 조회 전용 API(허용 목록에 조회 몇 개 추가) |
| `toss_orders.py` | 주문 전용 client. 허용: `POST /api/v1/orders`, `GET /api/v1/orders`, `GET /api/v1/orders/{id}`, `POST /api/v1/orders/{id}/cancel`. 요청 본문도 검사한다(`LIMIT`·`DAY`·정수 수량·`confirmHighValueOrder=false`) | 주문 |
| `trade_approval.py` | 확인 메일 발송, 답장 판독(코드만, 모델 없음), TOTP 검증 | Gmail |
| `trade_executor.py` | 상태 기계, 실행 직전 재확인, 주문·체결 대조, 결과 메일 | 주문 + 조회 |
| `trade_command.py` | `smith trade propose / run / status / halt / resume / enroll` | — |
| `trade_store.py` | `data/trades.db`(재무 원장과 별도 파일): 계획·다리·추가 전용 사건 기록·상태(중단 스위치, 쓴 TOTP 시간 칸, 실행 잠금) | 없음 |
| `totp.py` | RFC 6238(HMAC-SHA1, 6자리, 30초) 코드 계산·검증, 등록용 `otpauth://` 주소 | 없음 |

경계 테스트: 자문·보고서·메일 답변·조사 모듈(`adviser`, `narrative`, `qa`, `daily_qa`, `research` 등)이
`toss_orders`·`trade_executor`를 import하지 않음을 테스트로 고정한다. headless 모델 프로세스에는 지금처럼 shell·코드 실행 도구가 없다.

`trade_plan.py`가 쓰는 조회(조회 전용 `toss.py` 허용 목록에 추가 후보): `GET /api/v1/sellable-quantity`,
`GET /api/v1/prices`, `GET /api/v1/orderbook`, `GET /api/v1/price-limits`, `GET /api/v1/stocks/{symbol}/warnings`,
`GET /api/v1/commissions`, `GET /api/v1/market-calendar/{KR|US}`. 모두 GET이라 조회 전용 경계는 유지된다.

## 5. 워크플로

```
고객 요청 ──► [proposed] ──► [confirm_sent] ──► [approved] ──► [executing] ──► [done]
 (CLI·메일)    코드 계획서     확인 메일 발송     답장+TOTP 검증    다리별 실행      결과 메일·toss sync
                   │                │                 │               │
                   ▼                ▼                 ▼               ▼
               [rejected]      [expired]         [declined]     [halted] / [unknown]
               점검 실패         60분 경과          "취소" 답장      재확인 실패·반쪽 실행·응답 유실
```

1. **요청**: 두 입구.
   - 대화(Claude Code): `smith trade propose --sell CLS --qty all --then-buy-back` 같은 구조화된 명령. 모델 없음.
   - 메일: 재무 스레드에 "셀레스티카 전부 팔고 다시 사 줘"라고 답장. 기존 FR-18 판정(본인 발신·`SENT` 라벨)을
     통과한 질문 가운데 거래 요청으로 보이는 것만, 모델이 **초안 JSON**(종목·방향·수량 또는 "전량"·다시 사기 여부)을 만든다.
     코드는 초안을 원장 보유와 대조하고 고객 문장을 계획서에 그대로 인용한다. 모델은 가격·한도·계좌를 정하지 못한다.
2. **계획(코드)**: 사전 점검을 모두 통과해야 계획서가 생긴다. 하나라도 실패·누락이면 거래를 만들지 않고 이유를 답한다
   (모름은 통과가 아니다). 지정가는 현재가 기준 허용 폭(기본 매도 −1%, 매수 +1%) 안의 호가 단위 값으로 코드가 정한다.
3. **확인 메일** `[Smith][거래 확인] 셀레스티카 10주 매도 후 재매수 · 승인 코드 필요`: 무엇을·왜·얼마에·비용·세금 추정·
   위험·만료 시각·승인 방법. 계획 해시와 짧은 계획 번호를 싣는다(§6).
4. **승인**: 같은 스레드에 본인이 `승인 123456`(인증 앱 코드)으로 답장. 코드가 판독한다: 본인 발신·`SENT` 라벨·
   Smith 머리글 없음·확인 메일보다 늦게 보냄·계획이 아직 유효·TOTP 일치(±30초 1칸)·같은 TOTP 재사용 금지.
   모호하면(다른 글이 섞였거나 숫자가 틀림) 승인이 아니다. `취소`는 즉시 `declined`.
   인증 앱 코드는 특정 계획에 묶이지 않으므로 **승인을 기다리는 계획은 한 번에 하나뿐**이고, 새 요청은 그 계획이 끝날 때까지
   받지 않는다(대체하지 않음: 고객이 열린 확인 메일 하나에만 코드를 보내게 한다). 코드는 자기 확인 메일 이후의 것이어야 하고,
   **보낸 메일 전체(휴지통 포함)에서 그 승인 답장 한 통에만 있어야 한다.** 승인 직전에 Gmail 검색
   (`in:anywhere from:me after: before: "<6자리>"`, 코드 시각 앞뒤 약 2분, 메시지 ID만, 본문은 읽지 않음)으로 확인한다.
   복사본은 원본보다 늦으므로 승인 답장이 검색되면 원본도 함께 검색되고, 결과가 그 답장 하나가 아니면 승인하지 않는다.
   승인 답장이 아직 검색되지 않으면(색인 지연) 거부하지 않고 다음 실행에서 다시 본다. 코드 사용 기록과 `confirm_sent → approved`
   전환은 한 트랜잭션이며, 전환이 성공할 때만 실행한다.
   **남는 위험(2026-10-30 리뷰):** Gmail 계정을 완전히 장악한 공격자는 고객이 다른 곳에 보낸 코드의 원본을 영구 삭제하고 1분 안에
   열린 확인 메일로 옮겨 붙일 수 있다. 표준 인증 앱 코드는 계획 내용에 암호학적으로 묶을 수 없어, 메일만으로 승인하는 한 이 위험은 남는다.
   한도(한 건 500만·하루 1,000만 원), 결과 메일, `halt`가 피해를 제한한다. 이를 없애려면 승인을 PC의 `smith trade approve`(인증 앱 코드)
   같은 별도 경로로 옮겨야 한다(사용자 결정 대기).
5. **실행 직전 재확인**: 시장 개장, 보유·매도 가능 수량이 계획과 같음, 현재가가 계획 대비 허용 폭(기본 ±3%) 안,
   한도 여유, 같은 종목의 미체결 주문 없음, 중단 스위치 꺼짐. 하나라도 어긋나면 주문하지 않고 `halted` + 재제안 메일.
6. **다리 실행**: 다리 1 주문 → 주문 상세를 짧은 간격으로 조회해 `FILLED`를 확인(장 마감까지) → 다리 2.
   토스는 같은 종목에 반대 방향 미체결 주문이 있으면 409(`opposite-pending-order-exists`)로 거부하므로 순차 실행이 필수다.
   다리 2의 가격도 그 시점 현재가로 다시 정하고 계획의 상한(승인한 재매수 최고가) 안에서만 낸다.
7. **결과**: 체결 수량·평균 가격·수수료·세금·결제일과 추정 실현 손익을 `[Smith][거래 결과]`로 보내고 `toss sync`를 돌린다.
   부분 체결로 장이 끝나면 남은 수량은 자동 취소된 상태를 보고하고 새 승인을 받는다.

승인 확인은 지금의 15분 주기 작업으로 돌고, 확인 대기 중인 계획이 있을 때만 2분 주기 감시 작업을 켜는 것을 제안한다
(승인 뒤 실행까지 최대 15분이면 충분한지 §12).

## 6. 확인 메일 예 (합성 숫자)

```
[Smith][거래 확인] 셀레스티카 10주 매도 후 재매수 · 계획 T-7Q3K

요청하신 일: "셀레스티카 전부 팔고 다시 사 줘" (10/30 09:12 메일)
목적: 올해 해외주식 공제 250만 원 안에서 이익을 실현해 다음 해부터 세금 낼 이익을 줄임

1) 매도  셀레스티카(CLS) 10주 · 지정가 $285.20 이상 · 당일
2) 재매수 1이 모두 체결되면 같은 10주 · 지정가 최고 $288.10 · 당일
   예상 매도 금액 약 $2,852 · 수수료 약 $X · 재매수 비용 약 $2,881

세금 추정: 실현 이익 약 241만 원(현재 환율로 취득가까지 환산한 Smith 추정).
  실제 과세 이익은 매수 당시 환율로 계산하므로 다를 수 있습니다. 토스 앱의 '해외주식 양도세 예상'으로 한 번 확인해 주십시오.
위험: 1과 2 사이 몇 분 동안 가격이 오르면 같은 돈으로 덜 사게 됩니다. 2의 최고가를 넘으면 2는 내지 않고 다시 여쭙니다.

승인: 이 메일에 "승인 + 인증 앱 6자리"로 답장 (예: 승인 123456) · 취소: "취소"
만료: 10:15 (지나면 실행하지 않습니다)
```

## 7. 실행 규칙

- **주문 식별**: 다리마다 `clientOrderId = smith-<계획 ID 앞 16자>-<다리 번호>`를 `submitting` 기록 **후에** 보낸다.
  기록할 때 그 종목의 그날 주문 ID 목록(보내기 전부터 있던 주문)과 최초 송신 시각을 함께 남기고, 이 둘은 다시 바뀌지 않는다.
  시간 초과·연결 끊김·5xx·읽을 수 없는 2xx는 `unknown`이다. 확정은 항상 주문 목록 대조가 먼저다: 보내기 전에 없던 주문 가운데
  방향·수량·가격이 같고 송신 구간에 접수된 것이 정확히 하나면 Smith의 주문이다(둘 이상이면 고객 확인으로 남긴다).
  없으면 최초 송신 후 9분 안에서만, 그리고 처음 보내는 주문이 통과해야 할 점검(기능 켜짐, 중단 아님, 장 시간, 가격 이동, 미체결 주문)을
  지금 모두 통과할 때만 같은 키로 다시 보낸다. 다시 보낸 요청이 어떤 이유로든 실패하면 `unknown`을 유지하고, 9분이 지난 뒤
  완전한 목록에 없으면 '접수되지 않음'으로 확정한다. 확정 전에는 다음 다리로 가지 않는다.
- **한도는 실행 때도**: 다리를 `submitting`으로 바꾸는 같은 트랜잭션에서 그날(KST) 이미 나간 주문(결과 불명 포함) 합계와 이번 주문이
  하루 한도 안인지 확인한다. 계획을 만들 때 각각 한도 안이던 여러 계획이 함께 승인돼도 한도를 넘지 않는다.
- **계좌 고정**: 계획은 만들 때의 계좌 키에 묶인다. 설정 계좌가 바뀌면 그 계획으로는 주문·재전송하지 않는다. 계좌는 항상 종합매매(`BROKERAGE`)만.
- **같은 장**: 첫 주문이 들어간 정규장의 종료 시각을 계획에 남기고, 그 뒤의 다리(재매수)는 그 장 안에서만 낸다. 장이 끝났으면 멈추고 알린다.
- **전량 체결 뒤에만 다음 다리**: 매도가 일부만 체결되고 끝나면 재매수하지 않고 멈춰 체결 수량을 알린다.
- **재전송은 같은 KST 날짜 안에서만**: 하루 한도는 최초 송신 날짜에 잡혔으므로 자정을 넘긴 재전송은 하지 않고 목록 대조로만 확정한다.
  재전송 점검은 저장된 가격·수량 그대로 하고(원화 금액이 처음 잡은 금액을 넘으면 보내지 않음), 외부 조회가 끝난 뒤 시계를 다시 읽어
  날짜·10분 유효 시간·중단을 확인한다. 재전송 전에는 지금 설정된 하루 한도로 그날 합계도 다시 본다. 첫 송신도 조회가 끝난 시각으로
  날짜와 계획 만료를 다시 확인한다.
- **중단과 송신의 순서**: 중단 플래그는 다리를 `submitting`으로 바꾸는 트랜잭션 안에서 다시 확인한다. 그보다 늦게 걸린 중단은
  다음 실행이 접수된 주문(목록 대조로 찾은 것 포함)을 곧바로 취소한 뒤 결과를 기록한다.
- **명확한 거부**(4xx with code)는 재시도하지 않는다. 429는 `Retry-After`를 따르되 실행 창 안에서 최대 3회.
- **토큰**: 클라이언트당 유효 토큰이 하나라 실행 중 다른 Smith 작업(`toss sync`)이 토큰을 새로 받으면 실행이 401을 받는다.
  실행 중에는 `toss sync`가 같은 잠금을 기다린다(잠금 순서: 원장 → 토스 실행). 401은 재발급 후 같은 `clientOrderId`로 한 번.
- **중단 스위치**: `smith trade halt`(설정이 아니라 원장 플래그, 즉시 적용)와 `[trading] enabled`(기본 `false`).
  둘 중 하나라도 꺼져 있으면 계획·실행 모두 하지 않는다. 진행 중 주문은 `halt` 시 Smith가 낸 미체결분만 취소한다.
- **원장**: `trade_plans`(계획·해시·만료·상태), `trade_legs`(다리·`clientOrderId`·`orderId`·상태·체결 필드),
  `trade_events`(추가 전용 감사 기록: 누가·언제·무엇을, 승인 메일 ID, TOTP 시각 칸 번호; 코드 값 자체는 저장하지 않음).
  계좌번호·`accountSeq`는 저장하지 않고 기존 불투명 계좌 키를 쓴다.
- **로그**: 계획 번호·다리 번호·상태·HTTP 상태·오류 코드·requestId만. 주문 응답 원문은 남기지 않는다.

## 8. 설정 (로컬, Git 제외)

```toml
[trading]
enabled = false                 # 켜기 전까지 계획도 만들지 않음
account = "toss-xxxxxxxx"       # 허용 계좌 하나 (불투명 키)
max_order_krw = 5000000         # 다리 하나의 최대 금액 (원화 환산)
max_daily_krw = 10000000        # 하루 합계 (매도+매수)
plan_ttl_minutes = 60
limit_band_pct = 1.0            # 지정가를 현재가에서 얼마나 떨어뜨릴지
drift_halt_pct = 3.0            # 승인 뒤 가격이 이만큼 움직이면 중단
```

매수 종목은 제한하지 않는다(사용자 결정 2026-10-30). 매수 유의 종목(정리매매·투자위험·투자경고·단기과열)은 코드가 막는다.

한도와 허용 계좌는 메일·모델이 바꿀 수 없다(FR 공통 원칙). 한도를 넘는 계획은 만들지 않고 이유를 답한다.

## 9. 셀레스티카 첫 적용에서 확인할 것

- **환율**: 해외주식 양도차익은 양도가액·취득가액을 각각 그 날의 기준환율로 원화 환산한다. 토스 API는 평균 단가(달러)만
  주므로 Smith의 241만 원은 근사다. 매수 당시 환율이 지금보다 낮았다면 실제 이익은 더 크고 250만 원을 넘을 수 있다.
  첫 실행 전 고객이 토스 앱의 양도세 예상 화면을 한 번 확인하거나, 매수 내역(날짜)을 원장에 넣어 코드가 계산한다.
- **공제 공유**: 같은 해 다른 해외주식 매도 이익(Hermes 운용 계좌 포함)이 있으면 250만 원을 나눠 쓴다.
- **연도 기준**: 과세 연도는 결제일 기준이다. 미국 주식은 체결 다음 영업일 결제이므로 연말 마지막 주는 피한다.
  지금(10월 말)은 여유가 있다. 서두를 이유가 없으므로 구현·시험을 마친 뒤 11월 중 실행을 제안한다.
- **전량 매도인 이유**: 일부만 팔면 과세 취득가가 선입선출로 계산돼 토스 앱의 평균 단가 기준 이익과 달라진다. 전량은 이 차이가 없다.

## 13. 구현 메모 (1단계)

- 한 번에 한 실행: 운영체제 파일 잠금(`data/trades.lock`, 프로세스가 죽으면 OS가 푼다). 오래됐다는 이유로 넘겨받지 않는다.
  보내기 직전에 그 다리가 여전히 이 송신을 기다리는지(상태·최초 송신 시각) 다시 확인한다.
- 정기 실행: `report run-due`가 15분마다 메일 답변 다음에 `trade_command.run_pass`를 부른다(`[trading] enabled`일 때만,
  열린 계획이 없으면 토스 호출도 없음). 계획이 끝나거나 멈추면 바로 `toss sync`로 보유를 갱신한다.
- 승인 확인은 확인 메일의 스레드와, 승인 코드 하나에 대한 보낸편지함 검색(ID만)을 읽는다(`gmail.readonly`가 필요, `smith mail login --read`).
  검색의 숫자 일치와 색인 지연은 실제 Gmail로 아직 확인하지 않았다(2단계 카나리에서 확인). 보고서 답변(FR-18)은 이 스레드를
  읽지 않으므로 "승인 123456"이 질문으로 답해지지 않는다.
- 한 실행 안에서 주문 체결을 약 1분 기다리고, 그 뒤는 다음 실행이 이어 받는다. 매도가 체결되면 같은 실행에서 재매수까지 간다.
- 결과·중단 메일은 새 스레드 `[Smith][거래 결과]`로 보낸다. 메일 실패는 사건 기록에 남기고 다시 보내지 않는다.
- 남은 일: 2단계 카나리(실계좌), 메일 자연어 요청 입구(4단계), `smith doctor`에 거래 상태 줄.
