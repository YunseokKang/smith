# 하루 일과 메일 설계 (개인 비서 1단계)

상태: 설계 초안 v0.1 / 2026-10-25. 사용자 결정은 "사용자 결정"으로, 구현 쪽 선택은 "선택"으로 표시한다.
요구사항은 `docs/requirements.md` FR-30(원칙)·FR-31(메일)·FR-32(날짜 DB). 아직 코드는 없다.

## 1. 역할 확장 원칙 (FR-30)

Smith는 재무 자문(PB)에 더해 생활 비서 역할을 맡는다. 첫 영역은 하루 일과다. 넓히는 방식은 세 가지 원칙을 따른다.

1. **영역마다 스레드, 스레드마다 자료.** 재무는 `[Smith][재무]`, 사건은 `[Smith][재무 · 사건 안내]`, 하루 일과는
   `[Smith][하루 일과]` 메일이다(사용자 결정 2026-10-25). 답장 질문은 그 스레드의 영역 자료만 받는다: 재무 스레드에
   일정·할 일이 들어가지 않고, 하루 일과 스레드에 재무 숫자가 들어가지 않는다. 가구·선호 기억(`memory.PINNED`)만 공통이다.
   주제를 모델이 추측하지 않으므로 잘못 고를 일이 없다. 아무 질문이나 받는 입구(주제 라우터)는 후속 단계다(§9).
2. **조회 전용.** Google Calendar는 `calendar.events.readonly`, Google Tasks는 `tasks.readonly` 권한만 요청한다
   (공식 문서 확인 2026-10-25). 일정 생성·변경·초대 응답·할 일 완료 처리·메일 전달은 하지 않는다. "내일 3시 회의
   옮겨 줘"에는 어떻게 하면 되는지만 답한다. 완료 처리는 고객이 앱에서 직접 한다(사용자 결정 2026-10-25).
3. **외부 글은 자료.** 캘린더 일정의 설명란, 할 일의 메모, 뉴스 본문은 남이 쓴 글일 수 있다. 지시로 취급하지 않고
   자료로만 넘긴다. 참석자 주소, 화상회의 링크·코드, 전화번호, 번지수는 모델에 보내기 전에 지운다(§5).

재무 실행 금지(AGENTS.md "Financial Execution Boundary")는 생활 영역에 "밖으로 나가는 동작 금지"로 같은 식으로 적용한다.

매일 06:00 Asia/Seoul, 일요일 포함, 재무 보고와 **별도 메일**(사용자 결정 2026-10-25). 위에서 아래로:

구현(2026-10-25): `daily.collect`(읽기, 출처별 실패) → `daily.assemble`(순수 조립) → `daily_html.render`; 공휴일은
`holidays.py`(연 단위 캐시 `data/holidays.json`, 30일 뒤 갱신, 연휴 = 주말+공휴일 3일 이상), 재무 날짜는 `daily.finance_dates`
(금통위 표, `TAX_CALENDAR` 통상 일정; "그해 고지서로 확인" 문구). 모델 프로즈가 없어도 메일은 코드 문장으로 완결되며,
프로즈는 날씨 문장·선물 제안·뉴스 요약·오늘의 문장만 바꾼다. `smith daily preview`는 `reports/`에 HTML을 쓰고 보내지 않는다.

제목: `[Smith][하루 일과] MM/DD (요일) · <준비물 또는 특보> · 일정 N건 · <가장 가까운 기념일 D-N>`. 분량 원칙(결론만,
1원·1분 단위 정밀도 금지)은 재무 보고와 같다.

**디자인(사용자 검수 2026-10-25)**: 재무 보고의 흰 바탕·단일 블루·검은 띠와 달리 **부드럽고 따뜻한 톤**이다 — 모래색 바탕
(`#f6efe6`), 크림 카드(`#fffdf9`), 베이지 머리 카드(`#f3e6d6`), 테라코타 포인트(`#b95b2a`), 상태 배지 대신 인사말("좋은 아침입니다"
/ 휴일엔 "편안한 휴일 아침입니다"). 머리 카드에 **신호등 줄**: 날씨·미세먼지·꽃가루(관련 특보가 있으면 네 번째)를 네 단계
색(좋음 `#2e9e44` ● / 보통 `#e9a800` ▲ / 나쁨 `#e3542a` ■ / 매우나쁨 `#a51c1c` ■, 자료 없음·계절 밖 회색 ○)으로 보이되, 색만으로
뜻을 싣지 않도록 **모양과 낱말을 항상 함께** 적는다(dataviz 상태색 규칙; 네 색은 2026-10-25 카드 바탕에서 검증 — 정상 시력 ΔE
16.7, 색약 9.7 통과, 노란색은 명도·대비가 낮아 낱말·모양이 보완). 등급 매핑은 `weather.signals`: 날씨는 규칙이 켜지면 보통,
눈·강수 70%↑·폭염·강추위는 나쁨, 관련 특보는 매우나쁨; 미세먼지는 공식 4등급 그대로(기관지 예민 때 '보통' 윗부분에 "기관지 주의"
낱말); 꽃가루는 지수 0~3. 카드는 접기 없이 모두 열린 짧은 카드다. 날짜 줄에 **어느 구 날씨인지**(`[daily.weather] label`)와
대기질 줄에 측정소를 적는다(사용자 요청 2026-10-25).

**그림**(사용자 요청 2026-10-25, `daily_art.py`): 보기만 해도 기분 좋아지는 캐릭터. 인사 카드 오른쪽에 **날씨 요정**(고정)과
그날의 날씨 그림(코드 규칙: 관련 특보 → 폭풍, 눈, 비(우산), 미세먼지 나쁨 → 마스크, 꽃가루 높음 → 재채기, 폭염, 강추위, 강풍,
흐림, 구름많음, 맑음), 오늘의 문장 왼쪽에 **기분 그림**(쓰기 모델이 14개 목록에서 고름, 없으면 계절·날짜로). 그림은 Microsoft
Fluent Emoji 3D(MIT, `assets/daily/`에 28개 동봉, 라이선스 파일 포함)라 아침에 다운로드에 기대지 않는다. 메일에서는 `cid:`로
참조하는 인라인 첨부(`gmail.send(images=)`, `multipart/related`, disposition inline), 미리보기 파일에서는 data URI. 공휴일·주말이면 ⓪·①의
어조가 출근이 아니라 휴일 기준이다. 일정이 없는 날은 "오늘 등록된 일정이 없습니다"가 한 줄이고 블록을 지어내지 않는다.

후속(요구사항에만 기록, 1단계 밖): 일정 살 붙이기("에버랜드 가기" → 그날 행사·식당, 웹 조사), 일요일 저녁 주간
미리보기, 저녁 "내일 준비" 메일. 바탕화면 타임박싱 플래너 연동은 하지 않는다(사용자 결정 2026-10-25).

## 3. 자료 출처와 결정적 계산

모든 수집은 `run-due`가 발송 직전에 한다. 실패한 출처는 그 블록을 "오늘 받지 못함(출처, 코드)"으로 표시하고 나머지는
보낸다(AGENTS.md "Failure visibility"). 어떤 출처도 0이나 "없음"으로 대체하지 않는다.

### 3.1 날씨 (⓪)

- 위치는 **구 단위**(사용자 결정 2026-10-25). 로컬 설정 `[daily.weather]`에 기상청 격자 좌표(`nx`, `ny`)와 에어코리아
  측정소(또는 시·도)를 둔다. 주소는 어디에도 없고, 모델에는 날씨 값만 간다. 거주 구는 원장의 `region`과 같다.
- 출처(공공데이터포털, 한 계정 키로 서비스별 활용 신청). 키는 실거래가 수집이 이미 쓰는 `datagokr` 키와 같은 계정 키라서
  OS 자격 증명 저장소(`credentials.load_api_key("datagokr")`)의 것을 그대로 쓴다. 2026-10-25 실제 호출로 확인한 끝점:

  | 서비스 | 끝점 | 확인 |
  |---|---|---|
  | 기상청 단기예보 | `1360000/VilageFcstInfoService_2.0/getUltraSrtNcst`(초단기실황)·`getVilageFcst`(단기예보), 격자 `nx=62, ny=123`(분당구; 격자표로 재확인) | 정상 |
  | 기상청 기상특보 | `1360000/WthrWrnInfoService/getWthrWrnList`, 조회 기간 최대 6일, `stnId`(108 전국; 수도권 코드는 구현 때 확인) | 정상 |
  | 기상청 꽃가루 3.0 | `1360000/HealthWthrIdxServiceV3/getOakPollenRiskIdxV3`·`getPinePollenRiskIdxV3`(3~6월), `getWeedsPollenRiskndxV3`(기상청 철자 그대로, 8~10월), `areaNo=4113500000`(분당구), `time=YYYYMMDD06` | 정상(참나무·소나무는 계절 밖 코드 99) |
  | 한국천문연구원 특일 | `B090041/openapi/service/SpcdeInfoService/getRestDeInfo` | 정상 |

  분당 62·123으로 검증), 측정소, 예보 권역, 꽃가루 지역 코드, 특보 관련 지역어. 단기예보는 당일 02시 발표분 전체(약 900행)에서
  오늘·내일의 TMN/TMX(없으면 시간별 TMP의 최소·최대), 깨어 있는 시간(06~23시)의 최대 강수확률·강수 시간·형태, 정오 하늘,
  최대 풍속을 뽑는다. 초단기실황은 40분 전의 정시 값. 특보는 `getPwnStatus`의 현황(t6)·예비특보(t7) 글을 줄 단위로 읽어 지역어가
  들어간 것만 '관련'으로 본다. 에어코리아는 측정소 1시간 값과 권역 PM2.5 예보 등급. 꽃가루는 세 수종 각각(계절 밖은
  "제공 기간 아님"). 출처마다 따로 실패하고(`failures`), 모델 입력에는 좌표·측정소 주소·키가 가지 않는다. `smith weather`.

  | 조건 | 준비물·행동 |
  |---|---|
  | 강수확률 ≥ 50% 또는 강수 형태 비·소나기 | 우산 |
  | 강수 형태 눈·진눈깨비 | 대중교통 권장, 운전 주의 |
  | 최저 ≤ 5℃ 또는 일교차 ≥ 10℃ | 외투(아침·저녁 쌀쌀) |
  | 최고 ≥ 30℃ | 물·양산, 한낮 외출 주의 |
  | 특보(태풍·호우·대설·강풍·한파·폭염) | 맨 위 빨간 띠, 외출 자제 또는 주의 |
  | 미세먼지·초미세먼지 '나쁨' 이상 | 마스크, 환기 자제 |
  | 꽃가루 위험지수 '높음' 이상(소나무·참나무 4~5월, 잡초류 8~10월) | 마스크, 창문 닫기, 외출 뒤 세안 |

- **기관지 예민 규칙**(사용자 2026-10-25: 기관지가 약해 꽃가루·대기질에 예민함; 로컬 설정 `airways_sensitive = true`):
  대기질과 꽃가루는 ⓪ 안에 **항상 한 줄**을 차지하고(값이 좋아도 "좋음"이라고 적음), 경고는 한 단계 먼저 켠다 —
  초미세먼지 '보통'의 윗부분(PM2.5 26~35 ㎍/㎥)과 꽃가루 '보통'부터 주의. 출처: 에어코리아 측정소 실시간 값, 기상청
  꽃가루농도위험지수 조회서비스(3.0, 시군구 단위, 오늘·내일). 꽃가루 자료는 계절 밖이면 "제공 기간 아님"으로 적는다.

### 3.2 일정 (①)과 할 일 (⑤)

- Google Calendar API v3 `events.list`(기본 캘린더, 오늘 00:00~23:59 현지, `singleEvents=true`, `orderBy=startTime`).
  종일 일정(`start.date`)은 시간 없는 일정으로, 시간 있는 일정은 시간순. 둘이 섞이면 종일 일정이 먼저다.
- 겹치는 두 일정, 15분 미만 간격은 코드가 표시만 한다. 이동 시간 계산은 하지 않는다(주소를 쓰지 않으므로).
- Google Tasks API `tasks.list`(`showCompleted=false`, `dueMax=오늘`)로 기한이 지난 미완료 할 일을 받아 기한이 가까운 순
  5개. 고객은 Google 캘린더 앱의 **'할 일'**로 할 일을 만들고 끝나면 완료로 바꾼다(사용자 2026-10-25). 캘린더 앱의
  '할 일'은 내부적으로 Google Tasks이므로 `tasks.readonly`로 그대로 읽힌다. 첫 조회(`smith agenda tasks`)에서 실제로
  보이는지 확인하고, 비어 있으면 `smith doctor`가 알린다. 캘린더 일정 자체에는 완료 상태가 없으므로 지난 일정은 판정하지
  않고, Smith는 어느 쪽도 쓰지 않는다.
- OAuth: 지금의 Gmail OAuth 클라이언트에 `calendar.events.readonly`, `tasks.readonly`를 더해 `smith mail login --read --daily`
  로 한 번 재동의한다(권한 추가는 재로그인이 필요하다; 저장된 클라이언트를 재사용하므로 클라이언트 JSON은 다시 필요 없다).

## 4. 날짜 DB (FR-32)

위치 `data/people.json`(Git 제외, 원장 옆). 사람과 날짜를 분리해 계속 늘릴 수 있게 한다. 구현: `src/smith/people.py`,
`smith people check|list|today|path|add|date`(2026-10-25). 손으로 고쳐도 되며 읽을 때 검증하고(모르는 키·중복 id·없는
날짜는 항목 이름과 함께 거부), 저장은 임시 파일 뒤 교체라 잘못된 편집이 파일을 깨지 않는다.

```json
{
  "people": [
    {"id": "father", "label": "아버지", "relation": "father",
     "birth": {"calendar": "lunar", "year": 1960, "month": 9, "day": 4}},
    {"id": "spouse", "label": "와이프", "relation": "spouse",
     "birth": {"calendar": "solar", "year": 1989, "month": 2, "day": 22}}
  ],
  "dates": [
    {"id": "wedding", "label": "결혼기념일", "kind": "anniversary", "month": 8, "day": 28, "year": null},
    {"id": "passport-self", "label": "여권 만료", "kind": "expiry", "date": "2031-03-15", "remind_days": [60, 14]}
  ]
}
```

- `kind`: `birthday`(사람에서 파생), `anniversary`, `occasion`(발렌타인데이·화이트데이·크리스마스·어버이날·어린이날·설·추석;
  기본 목록은 설정 `[daily.occasions]`, 사용자 확인 대기), `expiry`(여권·면허·차량검사·전세 만기·검진 등 만료·갱신).
- **큰 기념일은 한국 나이**(사용자 결정 2026-10-25): 한국 나이 = 해당 연도 − 출생 연도 + 1. 환갑 61, 칠순 70, 팔순 80,
  구순 90, 아기 돌(만 1세), 결혼 10·20·30주년. 음력 생일의 큰 기념일은 그 해의 음력 생일 날짜다. `year`가 없는
  날짜(결혼 연도 미입력)는 주년을 계산하지 않고 그 사실을 `smith doctor`가 알린다.
- **알림 규칙**: 생일·기념일·occasion은 D-7과 당일, 큰 기념일은 D-30·D-7·당일, `expiry`는 `remind_days`(기본 30·7).
  알림은 해당 날의 메일에 한 번 실리고 원장(`daily_reminders`)에 기록해 지연 발송·재실행에도 중복이 없다. 메일을 놓친
  날의 알림은 다음 메일에 "지난 알림"으로 한 번 실린다. 14일 안의 날들은 알림과 별개로 한 줄 띠로 보인다.
- **모델에 가는 것**: 이름이 아니라 `label`(관계 호칭), D-N, 큰 기념일 여부, 선물 창(D-30·D-7)에만 만 나이. 생년월일·
  음력 날짜 자체는 가지 않는다. 선물·이벤트 제안의 취향은 고객 기억(`data/memory/*.md`)에서만 오고, 없으면 "취향을
  알려 주시면 더 맞춰 드립니다"라고 쓴다. 기념일 관련 웹 조사는 또래 벤치마크(FR-21 ③)처럼 "30대 여성 생일 선물"
  같은 일반 질문만 허용하며 이름·관계·기억을 넣지 않는다.

## 5. 모델 입력과 검증

- **쓰기 모델(`daily-writer-v1`)**: 날씨 값과 코드 준비물, 일정 표(제목·시작·끝·종일 여부; 장소는 숫자가 없는 장소명만;
  설명은 URL·메일 주소·전화번호·회의 코드 제거 뒤 200자), 할 일 제목·기한, 기념일 D-N·호칭·나이(선물 창), 검증된 뉴스
  5개, 공휴일, 재무 날짜 줄, 고정 기억과 관련 기억. 재무 숫자는 없다. 출력은 JSON(블록별 문장)이며 코드가 구조·타입을 검증한다.
- **조사 모델(`daily-research-v1`)**: 뉴스 질문만. 개인 데이터·기억 없음.
- **코드 검증**(`daily_writer.verify`, 구현 2026-10-25): 두 자리 이상 숫자는 입력 JSON에 있는 것만(없으면 그 칸을 버림), URL·
  이메일·전화번호 제거, 오늘의 문장에 사람 이름 귀속("— 처칠", "~의 말") 금지, 선물 제안은 오늘 알림의 키에만(다른 날 제안은
  버림), 취향 기억(`family` 주제 등에 그 호칭이 있는 사실)이 없는 사람의 제안에는 취향 요청 문장을 붙임, 뉴스 요약은 검증된
  ref에만, 길이 상한. 버린 칸은 코드 문장으로 대체되며(메일은 모델을 기다리지 않음) 사유는 시스템 노트용 `problems`로 남는다.
  일정·할 일 제목은 모델이 바꾸지 않는다(코드가 표에 그대로 싣고 모델은 한 줄 해설만).
- 호출은 보고서처럼 `advice_runs`에 감사 기록(종류 `daily`)하고 시간·출력 크기·재시도를 제한한다.

"내일 일정 보여 줘"는 질문이고, "기억해 둬"는 FR-19 추출이 그대로 동작한다. 실행 요청(일정 변경·메일 전달)은 거절하고
방법만 안내한다. 재무를 묻는 답장에는 "재무 메일에 답장해 주시면 그 자료로 답합니다"라고 안내한다.

### 6.1 조사 요청 (FR-33)

고객은 같은 스레드에서 조사를 맡길 수 있다(사용자 요구 2026-10-25): "오늘 일정에 든 ○○ 행사(장소·회사)를 상세히
보고해", "오늘 만나는 ○○○에 대해 알려진 정보를 조사해 확인한 내용을 보고해". 흐름은 질의응답에 조사 호출 한 번이 더
붙는 것이다: 질문 분류(코드 규칙 + 쓰기 모델의 `needs_research`) → 조사 모델(웹, 질문 본문과 그날 일정 제목만; 고객
기억·재무 데이터 없음) → 코드 검증(URL 도달·날짜, 매체) → 쓰기 모델이 확인됨·미확인으로 나눠 답장. 한 답장에 조사
호출 1회, 15분 상한, 하루 한도는 질의응답과 공유한다. 준비 사항은 7d에서 `qa.py`의 입력 선택과 함께 구현한다.

사람 조사는 비서가 회의 전에 하는 공개 자료 확인 수준으로 한정한다.

| 항목 | 규칙 |
|---|---|
| 범위 | 공개된 직업 정보만: 소속·직책·경력, 공개 발표·논문·기사·인터뷰, 회사 공식 페이지. 주소·가족·건강·재산·연락처·사생활·비공개 SNS는 찾지도 싣지도 않는다 |
| 출처 | 검색 엔진에 공개된 페이지만. 로그인 뒤에만 보이는 LinkedIn·사람인 페이지는 읽을 수 없고 읽지 않으며, 답장에 그 사실을 적는다 |
| 동명이인 | 질문이나 일정에서 얻은 단서(소속·직책·지역) **두 개 이상**이 맞을 때만 동일인으로 본다. 아니면 "동일인 미확인"으로 표시하고 단서를 더 달라고 한다 |
| 표기 | 사실마다 출처 URL·게재일. 코드가 도달을 확인한 링크만. 확인됨 / 한 출처만 / 미확인을 나눈다. 추정은 추정이라고 쓴다 |
| 저장 | 제3자 정보는 답장 본문과 원장의 질의응답 기록에만 남는다. 고객 기억(`data/memory`)에는 쓰지 않는다(FR-19 추출에서 제3자 사실 제외) |
| 거절 | 공개되지 않은 정보를 찾아 달라는 요청, 신원 추적·감시 성격의 요청은 하지 않고 이유를 적는다 |

행사·장소·회사 조사는 공식 페이지(주최·운영사·관공서)를 먼저 찾고 운영 시간·예약·요금·당일 행사·찾아가는 길처럼
그날 결정에 필요한 것만 싣는다. 메뉴·식당 추천은 공식 페이지나 복수 매체가 있는 것만 쓴다.

- 설정 `[daily]`: `enabled`(기본 false), `time = "06:00"`, `weekdays`(기본 7일), `news_count = 5`, `news_topics`,
  `[daily.weather]`, `[daily.occasions]`. 수신자는 재무 보고와 같은 설정된 본인 주소 하나다.
- `run-due`가 보고서와 같은 상태 기계로 발행한다(구현 `daily_send.py`, 2026-10-25): 원자적 claim(`daily_runs`, 회차 키 = 현지
  날짜; 수동 발송은 `날짜#manual-xxxx`로 따로), claim 시각이 토큰이 되어 임대(30분)가 끝난 실행은 쓰거나 보낼 수 없고, `building`
  → `sending`(메일 요청 **전에** 기록) → `sent|failed|unknown`. 결과 미상·임대 중 중단된 `sending`은 다시 보내지 않고, 깨끗한
  실패만 3회까지 재시도한다. 발송 시각이 회차보다 30분 넘게 늦으면 제목이 `[Smith][하루 일과 · 지연 발송]`이다. 놓친 날은
  나중에 보내지 않는다(어제 일정은 쓸모가 없다). 대신 그날의 알림은 `daily_reminders`에 기록이 없으면 다음 메일에 "지난 알림"으로
  한 번 실린다(최근 3일, 아직 지나지 않은 날만). 재무 보고와 같은 분에 두 메일이 나가며 서로 기다리지 않는다; `[daily] enabled`는
  `[reports] enabled`와 독립이다.
- `smith daily preview`는 보내지 않고 HTML·Subject를 보여 준다(`--model`로 뉴스·쓰기 모델 포함). `smith daily send`는 명시
  요청으로 즉시 발송하고(`--model` 선택), `smith daily status`는 최근 회차를 보인다.

## 12. 여행 모드: 위치 기반 자동 전환 (FR-34, **보류 · 다음 단계**)

사용자 결정 2026-10-25: 1단계에서 빼고 parking lot에 둔다. 아래는 그때 쓸 설계다.

고객은 해외 여행이 잦고, 여행 모드는 **등록이 아니라 실제 위치로 스스로** 켜지고 꺼져야 한다(사용자 요구 2026-10-25).
Smith는 집 PC에서 돌고 Google은 개인 계정의 위치를 주는 API가 없으므로, 위치는 폰이 알려 주고 예약 일정이 보완한다.

### 12.1 판정 신호 (우선순위 순, 코드)

| 신호 | 출처 | 설정 | 신뢰 |
|---|---|---|---|
| A 실제 위치 | 폰 자동화가 매일 현지 05:00과 **시간대가 바뀔 때** 본인 Gmail로 보내는 위치 메일. 제목 `[Smith][위치]`, 본문 `위도,경도[,정확도m]`. Gmail 필터가 라벨 `smith-location`을 붙이고 Smith는 **그 라벨의 최근 48시간 메일만** 읽는다(`gmail.readonly` 범위 안; 발신이 본인 주소이고 SENT 라벨이 있을 때만 인정, 본문은 숫자 두세 개만 받는 엄격한 파싱) | 폰에 자동화 1회 | 집(설정 좌표)에서 100 km 넘게 떨어지면 여행 중. 36시간 넘게 보고가 없으면 B로 |
| B 예약 일정 | Gmail이 캘린더에 자동 등록한 항공·기차·호텔 일정(Calendar API `eventType=fromGmail`, 2024-05부터 구분). 도착 공항·체크인 도시와 기간을 읽어 여행지·기간을 추정. 공항 코드 → 도시는 작은 IATA 표 또는 지오코딩 | 없음(Gmail 자동 등록이 켜져 있으면 됨) | 항공편+호텔이 맞으면 '확정', 하나면 '예정'으로 표시 |
| C 수동 | `smith daily trip add|remove 시작 끝 도시` | 명령 | 자동 판정이 틀렸을 때의 예외 |

판정 근거는 메일 상단 한 줄에 적는다: "여행 모드 · 파리 · 위치 보고 05:02 기준" 또는 "여행 예정 · 12/20 파리행 항공편 기준".
집으로 돌아오면(위치가 집 반경 안, 또는 귀국 항공편 뒤) 자동으로 분당·KST로 복귀한다.

### 12.2 여행 중 메일

- 발송 06:00 **현지 시각**. 회차 식별은 현지 날짜이며 `run-due`가 여행지 시간대로 마감을 계산한다.
- 날씨는 여행지 좌표로 Open-Meteo(무료, 키 없음, 전 세계: 기온·강수·바람·PM2.5). 시간대는 Open-Meteo `timezone=auto`,
  나라는 tzdata의 `zone1970.tab`, 도시 이름은 하루 한 번의 역지오코딩(없으면 "현지"). 기상청 특보 같은 공식 경보는 한국
  밖에서 받을 수 없으므로 "현지 기상 경보는 제공하지 않음"을 적고 수치만 보인다.
- 여행지 한 줄: 외교부 해외안전여행 여행경보 단계(공공데이터 API)와 그날 환율(원/현지통화, 금액 없음).
- 일정은 현지 시각으로 쓰고, 한국 시간대로 잡힌 일정은 괄호에 KST를 병기한다. 기념일·뉴스·오늘의 문장은 그대로 간다.
- 집 날씨 한 줄은 선택(설정).

### 12.3 개인정보

좌표는 `data/location/`에 7일만 두고 그 뒤 지운다. 모델에는 도시·나라·시간대·날씨만 가고 좌표·집 위치는 가지 않는다.

## 13. Keep 지식 창고 (FR-35)

사용자 결정 2026-10-25: Keep 메모는 오늘의 문장 재료를 넘어 **에이전트의 핵심 자산**(취향·생각의 기록)이다.

- **동기화**(`drive.py`, `keep.sync`): Google Takeout 예약 내보내기(Keep만, 매달, Drive 저장) → Smith가 하루 한 번
  (`run-due` 안, `sync.json`의 `last_checked`) Drive에서 `takeout-<stamp>-<part>.zip`만 이름으로 찾아 가장 새 내보내기의 모든
  part를 받고(크기 상한 300MB), `import_takeout`으로 `notes.json`을 갈아 끼운 뒤 zip을 지운다. 같은 stamp면 건너뛴다. Drive 권한은
  `drive.readonly`(구글 설계상 광범위)이므로 코드가 Takeout 이름 패턴 밖의 파일은 열지 않고 폴더를 훑지 않는다. 오류는 로그로만.
- **단위는 '항목'**: 첫 가져오기(2026-10-25)에서 고객의 메모는 대부분 월 단위 일기 노트("2026-04")에 날짜 글머리("0406 ㆍ…")로
  쓴 긴 문서였다(61개 노트 → 4천여 항목). 그래서 `keep.entries`가 글머리·날짜 토큰에서 노트를 쪼개 `Entry`(id `노트#번호`,
  항목 날짜, 라벨)로 만들고, 선택·검색·회전은 항목 단위로 한다. 생각 고르기는 1인칭·감정어가 있는 회고 항목을 올리고
  마크다운 제목·인용·연도 나열·영문 위주의 학습 메모와 `학습`·`근골격` 같은 라벨은 내린다.
- **저장·검색**(`keep.search`): `data/keep/notes.json`; 검색은 고객 기억과 같은 가중 글자 2묶음 방식(두 글자 한국어도 매칭,
  임베딩·외부 전송 없음). FTS5 trigram은 세 글자 미만 질의를 못 찾아 쓰지 않는다.
- **용도별 전달**: 오늘의 문장 ← `keep.thoughts` 6개(§3.5); 기념일 선물 제안 ← 그 호칭을 언급한 메모 2개(`family_notes`,
  취향 기억이 있는 것으로 간주); 하루 일과 답장 ← 질문과 관련된 메모 5개(`client_notes`). 항상 식별자 마스킹·300자. 웹 조사
  모델과 재무 스레드에는 넘기지 않는다.
- **후속**: 아무 질문이나 받는 입구(§9)의 1차 자료, 메모 변경 이력(새 내보내기와의 차이), 라벨 기반 민감 메모 제외 설정.

   만료일은 `smith people date ID --label "여권 만료" --kind expiry --on YYYY-MM-DD --remind 60,14`.
6. 캘린더는 지금처럼 기본 캘린더에, 할 일은 캘린더 앱의 '할 일'에 둔다. 바꿀 것은 없다.
7. **Keep 자동 동기화**(사용자 결정 2026-10-25, §13): [takeout.google.com](https://takeout.google.com) → "모두 선택 해제" →
   **Keep**만 체크 → "다음 단계" → 전송 방법 **"Drive에 추가"**, 빈도 **"1년 동안 매달 내보내기"**(사용자 설정 2026-10-25: 매달 12회), 형식 zip, 크기 2GB →
   "내보내기 만들기". 첫 내보내기는 바로 만들어져 몇 분~몇 시간 안에 Drive의 `Takeout` 폴더에 `takeout-….zip`으로 들어온다.
   그다음 `smith mail login --read --daily --drive`로 Drive 읽기 권한을 한 번 더 동의한다(동의 화면에 "Drive 파일 보기"가
   보이면 정상). 이후는 자동이다: 매일 한 번 Smith가 새 zip을 확인해 반영하고, `smith keep sync`로 바로 당길 수도 있다.
   1년 뒤 Takeout 예약을 한 번 갱신한다. `smith keep status|pick|search 단어`.
